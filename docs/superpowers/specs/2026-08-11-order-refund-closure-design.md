# 订单与退款真实闭环设计

## 目标

让跑腿订单从创建、接单、送达、确认收货到完成，以及退款从申请、审核、支付渠道确认到用户通知，始终存在一个可追溯、可恢复、可运营的真实状态。用户、骑手与后台必须看到同一事实；不能以页面标签、已提交申请或人工猜测代替支付和履约终态。

## 已批准范围

- 覆盖跑腿订单的用户端状态、确认收货、退款申请、后台审核和退款资金记录。
- 退款规则固定为：用户申请 -> 后台审核 -> 原支付渠道退款 -> 支付回调或主动查询确认 -> 通知用户；驳回退款后恢复原履约状态。
- 退款成功只以支付服务的成功回调或主动查询结果为准；不得通过页面按钮直接把订单或退款单改为成功。
- 后台人工完成仅用于渠道外人工打款，必须要求凭证号并留存操作审计。
- 对历史异常数据先只读审计和 dry-run；任何实际回填或修复命令必须由用户单独批准。
- 不更换支付渠道、不绕过现有微信退款回调、不新增并行订单或退款模型。

## 统一状态机

跑腿履约状态只允许以下迁移：

`pending_pay -> pending_accept -> accepted -> in_progress -> arrived -> completed`

- 骑手只能推进至 `arrived`，并同时写入送达时间、收货确认截止时间和配送节点。
- 用户只能确认自己处于 `arrived` 且没有退款、申诉或高风险冻结的订单；确认采用条件更新，成功后原子写入 `completed`、确认人、确认时间、结算可用时间和时间线节点。
- 系统仅在截止时间到期且没有退款、申诉或风险冻结时自动确认，使用与用户确认相同的服务方法。
- 已完成、已取消和已退款均为终态；重复请求返回当前结果或明确的状态变化提示，不得倒退到待接单。

退款状态独立于履约状态：

`none -> pending -> processing -> success | failed`

- 用户申请创建唯一的 `PaymentRefund`，并将业务订单标记为退款处理中，阻止继续派单、配送、确认收货和结算。
- 后台审核通过只允许 `pending -> processing`，由既有支付服务提交原路退款；审核驳回只允许 `pending -> failed`，并恢复订单的退款标记与原履约状态。
- 支付渠道回调或主动查询只允许 `pending/processing -> success`；该同一事务写入已退款金额、业务订单退款终态、资金流水、申诉联动和用户通知。
- 渠道失败写入失败原因并恢复订单的可履约状态；同一支付单存在其他处理中退款时不得过早恢复。

## 用户端事实呈现

订单列表、订单详情和详情页底部操作统一使用后端返回的原始履约状态、退款状态、退款原因和时间线，而不是用显示标签反推状态。

- `pending_accept` 显示“待骑手接单”；`accepted/in_progress` 显示“骑手配送中”；`arrived` 显示“已送达，待确认收货”；`completed` 显示“订单已完成”。
- `pending` 显示“退款审核中”；`processing` 显示“退款处理中”；`success` 显示“退款成功”；`failed` 显示“退款未完成”，包含可读原因与后续入口。
- 确认收货按钮只在 `arrived` 时显示并可操作；若有退款、申诉或风险冻结，显示禁止原因和对应处理入口，而不是无反馈失效。
- 每次订单、退款状态变更写入用户可查看的时间线，并发送站内通知；支付退款成功和失败应使用已有通知服务发送可追溯消息。

## 后台运营工作台

后台退款处理页应成为支付退款的唯一操作面，而非仅展示财务流水。

- 列表按审核中、渠道处理中、退款成功、退款失败筛选，展示退款单号、原订单号、用户、业务类型、申请原因、金额、创建/更新时间和失败原因。
- 详情关联订单履约时间线、送达证据、退款状态迁移、支付渠道回执和管理员操作日志。
- 具备 `order:refund` 权限的管理员可审核通过或驳回待审核申请；通过调用既有执行退款服务，驳回调用既有恢复服务。
- 仅渠道外人工打款记录允许人工确认完成，必须填写凭证号；微信退款处于处理中时只允许查询或等待回调，不能伪造成功。
- 退款记录和统一订单检索页均把退款状态置于履约状态之前，避免“已取消/待接单”掩盖退款处理进度。

## 历史异常处理与监控

新增只读审计输出三类异常：完成订单缺少确认信息、已送达超过截止时间未确认且未冻结、退款处理中超时或退款状态与支付退款单不一致。审计只输出订单/退款标识、当前状态、时间与推荐动作。

修复脚本默认 dry-run，不创建资金流水、不调用支付渠道；只有显式 `--apply` 且获得用户确认后，才针对审计输出的具体订单执行受条件约束的修复。支付退款终态仍由渠道回调或主动查询决定。

## 验收标准

- 单元/集成测试证明：骑手不能直接完成、送达后用户确认一次完成、重复确认幂等、退款/申诉/风险冻结阻止确认。
- 单元/集成测试证明：退款审核通过进入渠道处理，渠道成功才让订单退款成功，渠道失败或审核驳回恢复正确履约状态，重复回调不重复记账。
- 后台测试证明：退款列表能看到跑腿退款，审核动作按权限调用正确后端接口，失败原因和凭证可见。
- 小程序接口测试证明：订单列表与详情对同一订单显示相同终态；用户在送达、退款中、退款成功和失败时收到明确状态与允许操作。
- 本地构建和专项测试通过后，再进行三角色开发者工具验证；真实金额退款仅在用户另行授权后，以最小金额验证渠道回调与到账。
