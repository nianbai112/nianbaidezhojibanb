# 骑手 App 收入、结算、提现与申诉设计

**日期：** 2026-07-28
**状态：** 已确认
**范围：** 骑手收入中心、结算明细、钱包流水、提现申请与结算申诉

## 目标

让审核通过的官方骑手能够在独立 App 内核对每笔收入、查看结算进度、把已到账钱包余额提交提现，并对有争议的结算单发起申诉。后台继续使用现有骑手结算和提现审核菜单完成财务处理，不再建设第二套账。

## 资金边界

- 唯一资金链保持为 `RiderSettlement -> Wallet -> Withdraw`。
- 后台确认并支付骑手结算后，金额进入骑手钱包；骑手只能从钱包可用余额申请提现。
- 提现继续复用现有原子余额冻结、单笔处理中限制和后台审核/打款状态机。
- 结算申诉只产生待处理记录，不自动加钱、扣钱、修改结算状态或触发外部打款。
- 所有 App 接口必须同时校验登录、审核通过、官方骑手、区域绑定和收入功能开关。
- App 只读取当前骑手自己的结算、钱包、提现和申诉数据。

## 复用方案

采用现有 `RiderSettlement`、`RiderSettlementItem`、`Wallet`、`WalletTransaction` 和 `Withdraw` 模型。骑手结算的收入计算继续复用现有后台统一计算规则，避免 App 和后台分别计算跑腿、外卖、补贴后出现金额差异。

未采用：

- 结算单直接向微信或支付宝出款：会绕过钱包、提现审核和既有对账链。
- 复用用户订单申诉：其退款、用户补偿、骑手处罚动作与骑手结算争议不属于同一权限和资金语义。
- 新建另一套骑手钱包：会制造双余额和重复出款风险。

## 后端设计

### 骑手专用接口

在现有 `/rider-app` 控制器下增加：

- `GET /rider-app/income/overview`：钱包余额、冻结金额、今日/本月已赚、待结算金额、处理中提现金额。
- `GET /rider-app/income/transactions`：当前骑手钱包流水，支持分页和类型筛选。
- `GET /rider-app/settlements`：当前骑手结算列表，支持分页和状态筛选。
- `GET /rider-app/settlements/:id`：当前骑手结算详情及所含订单明细。
- `GET /rider-app/withdrawals`：当前骑手提现记录。
- `POST /rider-app/withdrawals`：提交提现申请，内部调用现有 `FinanceService.withdraw()`。
- `POST /rider-app/settlements/:id/appeal`：对本人结算单提交一次结算申诉。

所有返回金额统一转换为 number，响应字段同时保持 App 当前使用的 snake_case 风格。分页上限为 50。

### 收入口径

- 今日/本月收入使用后台生成骑手结算时的同一订单筛选和计价规则。
- 跑腿收入包含配送费与小费；外卖收入使用平台骑手配送费与有效补贴口径。
- 退款中、已退款、未确认收货和不具备结算资格的订单不计入。
- 待结算金额只统计尚未被有效结算单覆盖的订单。
- 已支付结算以钱包 `COMMISSION` 流水为到账事实，不从订单金额再次累加钱包余额。

### 结算申诉字段

在 `RiderSettlement` 增加一组单次申诉字段：

- `appealStatus`：`pending`、`processing`、`resolved`、`rejected` 或空。
- `appealReason`：骑手申诉说明。
- `appealImages`：最多三张凭证图片。
- `appealReply`：后台处理说明。
- `appealedAt`、`appealHandledAt`、`appealHandlerId`。

同一结算单只能存在一个申诉，使用数据库条件更新防止弱网重复提交。允许对待确认、已确认、已支付和已驳回结算单申诉；申诉不阻断后台原状态机，但后台在确认或打款前必须能看到待处理申诉提示。

PostgreSQL、MySQL schema 和正式增量迁移同步更新；不连接生产数据库。

### 后台处理

现有“财务管理 -> 骑手结算”增加：

- 申诉状态筛选和待处理数量。
- 结算列表申诉标识。
- 详情中展示申诉原因、凭证和时间。
- `受理`、`解决`、`驳回`操作，终态必须填写处理说明。
- 有待处理申诉的结算单执行确认或打款时二次确认。

处理操作校验现有 `finance:settlement` 权限、管理员区域数据范围，并写入 `AdminOperationLog`。处理申诉本身不提供自动资金按钮；需要调整金额时仍通过现有结算、负债或人工财务流程完成。

## App 设计

新增“收入中心”页面，从工作台余额卡和“我的 -> 收入与结算”进入。

页面包含四个区域：

1. **收入总览**：可提现余额、冻结金额、今日收入、本月收入、待结算金额。
2. **结算记录**：结算周期、订单数、配送费、奖惩、应付/实付金额和状态；可进入订单明细。
3. **钱包流水**：结算入账、提现冻结及其他钱包变动。
4. **提现与申诉**：填写提现金额、渠道、账号和实名；查看提现状态；从结算详情提交申诉说明和最多三张凭证。

提现按钮提交期间禁用。提交成功后立即刷新钱包和提现列表；失败保留输入并显示服务端原因。收入功能关闭时隐藏入口，直接访问页面时显示功能未开放。

## 错误与并发处理

- 余额不足、存在处理中提现、重复点击由现有 Redis 锁、事务和余额条件更新共同拦截。
- 非本人结算、提现或申诉统一按不存在/无权访问处理，不泄露他人数据。
- 同一结算重复申诉返回已有申诉状态，不创建重复记录。
- 钱包或收入接口部分失败时页面保留其他已加载区域，并提供重试。
- 上传凭证失败不提交申诉；成功上传的 URL 才能进入申诉数据。

## 验收

- App 展示的今日、本月、待结算和结算单金额与后台同一骑手同一周期一致。
- 跑腿与外卖结算明细都能查看，不能读取其他骑手数据。
- 后台支付结算后 App 钱包出现一笔且仅一笔 `COMMISSION` 流水。
- 提现申请只冻结一次余额，重复点击或弱网重试不能产生并发透支。
- 后台拒绝提现后余额解冻；确认打款后冻结金额扣除并显示成功状态。
- 结算申诉在后台骑手结算详情可见，处理回复回到 App；处理申诉不会自动改变资金。
- App 自动测试、后端相关测试和全量测试、后台类型检查与生产构建、Android/iOS 编译全部通过。

## 非目标

- 不接入新的微信、支付宝或银行卡自动出款 SDK。
- 不允许骑手自行生成、确认、支付或修改结算单。
- 不允许申诉直接触发补款、扣款、退款或外部转账。
- 不执行生产数据库迁移，不进行真实资金提现。
