# 跑腿主打功能闭环设计

**日期：** 2026-07-22

**适用范围：** `后端后台本地测试版` 后端与管理后台、`前端文件` 微信小程序

**状态：** 待用户书面确认后进入实施计划

## 1. 目标与边界

本设计把现有跑腿模块从“功能入口齐全”改造成可审计、可退款、可结算、可运营的完整交易链。核心规则已经确认：骑手只能标记送达，用户确认后完成；用户不操作时，送达满 24 小时自动确认；存在退款、未完结申诉或风控冻结时暂停自动确认和结算。

实施采用原地闭环，不重写整个跑腿模块。继续复用现有 `PaymentService`、`WalletService`、`NotifyService`、`OrderAppeal`、`DeliveryOrderNode`、`DeliveryRiskEvent`、`RiderSettlement`、Redis 锁和支付超时释放任务。

本轮不做以下扩散：

- 不迁移到另一套后端语言或新订单表。
- 不引入新消息队列、工作流框架或状态机依赖。
- 不删除历史订单、退款、申诉或结算数据。
- 万能任务在采购款托管完成前，不允许要求接单者垫资；此类任务先服务端拒绝，采购款托管作为独立后续子项目。

## 2. 单一写入口

新增一个专用 `ErrandLifecycleService`，只负责跑腿订单状态推进和与状态同时发生的副作用。它不替代 `ErrandService`，也不复制支付、申诉、通知和结算系统。

调用关系：

```text
小程序用户接口 ─┐
骑手接口       ─┼─> ErrandLifecycleService ─> Prisma 条件更新/履约节点
管理后台接口   ─┤                           ├> PaymentService
退款回调       ─┤                           ├> NotifyService
定时任务       ─┘                           └> 骑手状态与结算资格
```

禁止 `ErrandAdminService`、支付回调和定时任务直接更新跑腿订单终态。所有写操作必须包含：

1. 操作者和订单归属校验；
2. 管理员区域数据范围校验；
3. 当前状态和退款状态条件更新；
4. 同事务履约节点与必要账务记录；
5. 事务提交后的通知；
6. 幂等返回或明确的状态冲突错误。

## 3. 履约状态机

复用现有状态值，避免无意义的历史状态迁移。`arrived` 的正式含义改为“已送达，等待确认”。

```text
pending_pay
  -> pending_accept
  -> accepted
  -> in_progress
  -> arrived
  -> completed
```

分支状态：

```text
pending_pay/pending_accept -> cancelled
可退款状态                -> refundStatus: none -> refunding -> refunded/partial
申诉处理中                -> 原履约状态不变，但冻结自动确认和结算
```

`status` 表示履约状态，`refundStatus` 表示资金退款状态。发起退款时不把配送中的订单伪装成已退款；全额退款最终成功后才将 `status` 同步为 `refunded`，部分退款保留原履约终态并把 `refundStatus` 记为 `partial`。

合法操作如下：

| 操作 | 操作者 | 前置状态 | 目标状态 | 必须副作用 |
|---|---|---|---|---|
| 支付确认 | 支付回调/余额事务/零元激活 | `pending_pay` | `pending_accept` | 消费权益、通知接单池 |
| 接单 | 合格接单者/有权限管理员 | `pending_accept` | `accepted` | CAS 占单、骑手忙碌、履约节点 |
| 开始配送 | 当前骑手 | `accepted` | `in_progress` | 校验取件凭证、记录取件时间 |
| 标记送达 | 当前骑手 | `in_progress` | `arrived` | 校验送达证据、写送达时间和确认截止时间、释放运力 |
| 用户确认 | 下单用户 | `arrived` | `completed` | 写确认时间/确认来源、生成结算资格时间 |
| 自动确认 | 系统 | `arrived` 且超过 24 小时 | `completed` | 排除退款/申诉/风控冻结，记录系统确认 |
| 未接单取消 | 下单用户/有权限管理员 | `pending_pay/pending_accept` | `cancelled` | 释放权益；已支付则发起原路退款 |
| 后台取消履约单 | 有权限管理员 | `accepted/in_progress/arrived` | 不直接取消 | 必须先创建售后处置，确认责任和退款方案 |

骑手不再拥有 `completed` 写权限。重复操作以 `updateMany(where: 旧状态)` 抢占一次；抢占失败返回“订单状态已变化”，不重复写节点、退款或结算。

## 4. 数据模型

### 4.1 `ErrandOrder` 增量字段

| 字段 | 类型 | 用途 |
|---|---|---|
| `receiptConfirmDeadline` | `DateTime?` | 骑手送达后的自动确认截止时间 |
| `receiptConfirmedAt` | `DateTime?` | 用户或系统真正确认收货时间 |
| `receiptConfirmedBy` | `String?` | `user/system/admin/legacy` |
| `settlementEligibleAt` | `DateTime?` | 确认后 24 小时售后冷静期结束时间 |
| `pricingSnapshot` | `Json?` | 基础价、距离、重量、时段、规格、小费、优惠、配置版本的服务端快照 |

继续使用现有 `deliverTime` 表示骑手送达时间，`completeTime` 表示最终确认时间。退款冻结和申诉冻结不增加易漂移的布尔字段，分别从 `refundStatus`、未完结 `OrderAppeal` 和未处理 `DeliveryRiskEvent` 推导。

### 4.2 骑手结算明细

新增 `RiderSettlementItem`，替代只把来源订单塞入结算备注 JSON 的做法：

- `settlementId`、`orderType`、`orderId`、`riderId`；
- `deliveryFeeAmount`、`tipAmount`、`rewardAmount`、`penaltyAmount`、`payableAmount`；
- `status`：`included/reversed`；
- `reversalAmount`、`reversedAt`、`reverseReason`；
- `@@unique([orderType, orderId])` 防止同一订单重复结算。

结算总额由明细聚合生成。退款或申诉发生时可准确找到原结算项目，而不是解析备注猜测来源。

已支付结算发生退款时新增 `RiderLiability`：记录 `riderId`、`orderId`、`refundId`、应追偿金额、已追回金额、`open/partial/settled` 状态和原因，`@@unique([orderId, refundId])` 防止重复追偿。提现入口存在未结清负债时拒绝提现；后续结算先抵扣负债，再形成可支付金额。

### 4.3 跑腿评价

新增最小 `ErrandReview`：`orderId` 唯一，记录 `userId`、`riderId`、1 至 5 星、最多 6 个标签、500 字内容、最多 9 张图片和审核状态。只有已确认且未全额退款的订单可以评价。奖励和处罚读取真实评价，不读取前端统计值。

### 4.4 区域闭环开关

在现有跑腿扩展配置中增加：`closureVersion=1|2`、`autoReceiptEnabled`、`settlementV2Enabled`。版本 1 保持旧读兼容但禁止骑手直接完成；版本 2 启用用户确认、新结算明细和自动确认。灰度和回滚只调整这些开关，不删除交易数据。

## 5. 服务端权威报价

新增纯计算的 `ErrandQuoteService`，供报价预览和创建订单共同调用，避免两套公式。

服务端不再接受客户端 `price`、`computed_fee` 或 `distance` 作为金额依据。计价顺序固定为：

```text
基础服务费
+ 规格加价
+ 服务端坐标计算的距离加价
+ 重量加价
+ 时段/夜间加价
+ 指定认证骑手加价
+ 小费
- 优惠券
- 会员优惠
= 应付金额
```

约束：

- 规格必须属于当前区域，且 `applyTo` 与任务类型匹配；缺失或跨区域直接拒绝。
- 经纬度必须在合法范围内；距离用服务端坐标计算，不能使用客户端传入公里数。
- 配送计价距离按任务顺序计算：从第一个有效取件坐标开始，依次经过不同取件点，最后到送达坐标；每段使用 Haversine 距离并求和。缺少必要坐标时拒绝计价，不用客户端距离兜底。
- 超出后台最大距离或最大重量直接拒绝创建。
- 小费必须大于等于 0，普通自定义小费上限 100 元。
- 客户端提交 `client_quote_pay_amount` 只用于发现页面报价已经变化；服务端重新计算不一致时返回 `QUOTE_CHANGED` 和新报价，不创建订单。
- `payAmount = 0` 时在创建事务内直接进入 `pending_accept`，支付渠道记为 `free`，不调用微信支付。
- `pricingSnapshot` 保存全部组成项和后台配置更新时间，客服和财务可还原订单为什么是这个价格。

报价接口不占用优惠或会员权益。创建订单时才以原子条件更新预占优惠和权益；支付成功或零元激活后转为已消费，支付关闭、超时或显式取消时通过现有释放服务恢复一次。

API 契约：

- `POST /errand/order/quote`：登录用户提交任务、地址、规格、重量、预约时间、小费和优惠选择，返回服务端金额组成、限制提示和 `quoted_at`。
- `POST /errand/order/create`：沿用现有入口，但忽略客户端金额；重新计算并比较 `client_quote_pay_amount`，变化时返回 `409 + code=QUOTE_CHANGED + quote`。
- 订单详情统一返回 `pricing_breakdown`、`allowed_actions`、`receipt_confirm_deadline` 和 `settlement_state`。

万能任务预算统一按“元”传输和存储，删除按数值大小猜测分/元的逻辑。采购款托管上线前，服务端拒绝“需接单者先行垫付”的万能任务，并在小程序明确提示。

## 6. 支付和退款

微信支付继续以支付回调为权威。余额支付继续使用已有原子扣款事务，但修正前端入口条件。

统一退款按 `PaymentOrder.channel` 分支：

- `wx_pay`：调用微信退款，最终回调幂等推进 `PaymentRefund`、`PaymentOrder` 和 `ErrandOrder`。
- `balance`：同一数据库事务内增加用户余额、写 `WalletTransaction(REFUND/BALANCE)`、完成 `PaymentRefund`、更新支付单累计退款和业务退款终态。
- `free`：不创建资金退款，只释放优惠、会员和补贴预占。

退款只允许基于真实可退余额，禁止负数、超额和重复处理中退款。用户取消、后台售后、申诉裁决都调用相同退款方法。

退款请求外部调用失败时：

1. 订单保留 `refundStatus=refunding`，不恢复配送；
2. `PaymentRefund` 记录失败原因；
3. 创建跑腿风险事件和后台异常任务；
4. 通知用户“退款处理中，平台正在重试”；
5. 运营后台提供受权限控制的“重试退款”，不提供手工直接改成成功。

## 7. 申诉、确认和结算

创建跑腿申诉后，不改变正常履约状态，但该订单立即被以下查询排除：

- 24 小时自动确认；
- 骑手结算生成；
- 奖励发放；
- 提现可用金额计算。

申诉处理增加明确的 `resolutionAction`：`no_action`、`full_refund`、`partial_refund`、`compensate_user`、`penalize_rider`。管理员必须填写处理说明。需要退款的申诉先进入 `processing`，只有退款成功或形成可重试退款记录后才进入 `resolved`。

`compensate_user` 使用平台承担的钱包补偿：增加用户余额、写 `WalletTransaction(REWARD/BALANCE)` 和平台支出流水；它不篡改原支付退款额。`penalize_rider` 在未支付结算中写入罚款明细，已支付结算则创建 `RiderLiability`。每个动作以申诉事件 ID 作为幂等来源。

新增/调整 API：

- `POST /errand/order/:id/confirm-receipt`：仅下单用户可从 `arrived` 确认；退款或未完申诉存在时返回冲突。
- 骑手现有状态接口继续接受 `arrived`，明确拒绝 `completed`。
- 管理后台现有派单、取消接口路径保持兼容，但内部转交 `ErrandLifecycleService` 并返回 `allowedActions`。
- 申诉后台更新 DTO 增加 `resolutionAction`、`refundAmount`、`riderPenaltyAmount`；金额动作与事件记录必须幂等。

订单进入 `completed` 后设置 `settlementEligibleAt = receiptConfirmedAt + 24 小时`。结算候选必须同时满足：

- `status=completed`；
- `receiptConfirmedAt` 非空；
- `settlementEligibleAt <= 当前时间`；
- `refundStatus` 不是 `refunding/refunded`；
- 没有 `pending/processing/waiting_user` 申诉；
- 没有未处理的冻结级风控事件；
- 没有已存在的 `RiderSettlementItem`。

若退款发生在结算确认前，撤销结算明细；结算已支付后退款，则生成结算冲正：优先扣除骑手可用余额，不足部分形成待抵扣负债，冻结提现并从后续结算中抵扣。所有冲正保留订单、退款和原结算明细引用。

## 8. 隐私、区域和接单权限

接口按阶段返回不同视图：

| 视图 | 可见内容 |
|---|---|
| 公共已完成动态 | 服务类型、模糊区域、金额区间、时间、匿名骑手；无地址、电话、坐标、取件码、任务原文 |
| 待接单池 | 校区/片区、粗略取送位置、任务类型、服务费、预计距离；无电话、精确地址、取件码 |
| 已分配骑手 | 当前订单完整取送信息和必要凭证 |
| 下单用户 | 自己订单完整信息、骑手公开资料和订单内位置 |
| 管理员 | 仅数据范围内完整信息，敏感字段默认遮罩，操作时记录审计 |

骑手位置接口必须登录，并验证调用者是该订单下单用户、当前骑手本人或有区域权限的管理员；订单必须处于有效履约状态。全局在线骑手接口增加区域参数和数据范围，不再展开身份证、支付宝账号等数据库字段。

正常接单、后台派单和转单统一校验：同区域、账号已审核、在线、未冻结、运力未超限、订单风险允许、订单仍未被占用。转单同时校验目标骑手与订单区域一致。

## 9. 小程序与运营后台

### 9.1 用户端

- `arrived` 显示“已送达，等待确认”，展示自动确认倒计时。
- 提供“确认收货”和“有问题，提交申诉”两个互斥主操作。
- 退款、申诉中隐藏确认按钮并解释冻结原因。
- 已确认且未全额退款的订单展示评价入口。
- 支付弹窗只在跑腿订单展示可用的余额支付；零元单不拉起微信支付。
- 接单前数据使用脱敏视图，接单成功后刷新完整详情。

### 9.2 骑手端

- 删除直接完成按钮，改为“已送达”。
- 根据风险结果动态要求图片、定位和备注；缺少必填证据不能提交。
- 展示“用户待确认/预计自动确认时间/申诉冻结/已进入结算”等状态。
- 转单列表只显示同区域且有接单资格的骑手。

### 9.3 管理后台

跑腿订单详情抽屉新增：服务端计价明细、履约时间线、送达凭证、自动确认截止时间、申诉冻结、退款单、结算明细和冲正记录。

操作按钮由服务端返回的 `allowedActions` 控制，不再由前端自行猜测。区域管理员只能处理授权区域。取消履约中订单时必须选择责任方、退款金额和是否处罚骑手。

异常中心至少展示：报价篡改尝试、退款失败、超时未接单、超时未送达、送达证据缺失、跨区域转单、自动确认冻结、结算冲正失败。所有异常支持指派、备注、处理和历史追踪。

## 10. 通知

直接复用 `NotifyService.createAndDispatch` 及其失败重试能力。通知场景包括：支付成功进入接单池、骑手接单、开始配送、已送达待确认、确认收货、自动确认、退款发起/成功/失败、申诉创建/处理、转单结果和结算异常。

订单状态事务不依赖外部通知成功。通知持久化后发送站内信和 WebSocket；微信订阅消息只在用户已经授权对应场景时发送。后台能够看到失败原因并重试。

## 11. 迁移、发布和回滚

### 11.1 数据迁移

迁移全部为新增字段和新增表，不删除历史字段：

- 历史 `arrived`：按 `deliverTime`，缺失时按 `updatedAt`，生成确认截止时间。
- 历史 `completed`：`receiptConfirmedBy=legacy`，但不自动写入新结算明细；先输出历史订单/现有结算对照报告，由财务确认后再补链。
- 历史 `completed` 同时令 `receiptConfirmedAt=completeTime`，但保持 `settlementEligibleAt=null`，因此不会被新结算查询自动选中。
- 新结算明细只处理启用闭环版本后的订单，避免旧备注结算重复入账。
- 万能任务历史预算不自动换算，保留原值并标记 `legacy_budget_unit_unknown`，由运营按订单核对。

### 11.2 灰度顺序

1. 先执行数据库迁移并部署兼容旧行为的后端；
2. 部署管理后台，确认异常中心、退款重试和区域权限可用；
3. 发布小程序确认收货、证据提交和脱敏视图；
4. 按区域开启闭环开关；
5. 最后启用自动确认和新结算生成。

### 11.3 回滚

关闭区域闭环开关即可停止新自动确认和新结算生成，保留已写入的履约节点和资金记录。代码回滚不回滚已成功退款、余额流水、微信交易和已支付结算；这些只能通过带引用的冲正处理。新增字段和表暂不删除，确保旧版本仍能读取原有字段。

## 12. 监控与修复工具

上线看板至少监控：

- 各状态订单数量和最长停留时间；
- 报价变更/篡改拒绝次数；
- 15 分钟未支付、10 分钟未接单、配送超时、24 小时待确认数量；
- 自动确认成功、跳过和失败数量及原因；
- 退款处理中超过 30 分钟、退款失败和重复回调；
- 未完申诉、被冻结结算金额、结算冲正欠款；
- 接单前敏感字段泄露回归检查和位置接口 403 数量。

修复工具只能执行幂等领域动作：重新计算允许操作、重试退款、重试通知、重跑单笔自动确认、重建单笔结算明细。禁止提供“直接修改状态为完成/退款成功/已结算”的按钮。

## 13. 测试与上线验收

### 13.1 自动化测试

- 报价：客户端价格无效、跨区域规格、距离/重量上限、负小费、零元单、报价变化。
- 状态机：每个合法迁移、所有非法跳转、重复请求、并发接单、并发送达和退款。
- 确认：用户确认、24 小时自动确认、退款冻结、申诉冻结、风控冻结、重复任务。
- 退款：微信成功/处理中/失败/重复回调；余额全额/部分/重复退款；零元释放。
- 结算：确认前不可结算、冷静期、申诉排除、唯一明细、退款前撤销、付款后冲正。
- 权限：他人订单、跨区域管理员、公共接口脱敏、位置接口归属、跨区域转单。
- 小程序：确认收货、倒计时、余额入口、零元单、申诉冻结和接单前后字段变化。

### 13.2 真实环境验收

使用同一测试区域和真实 PostgreSQL，至少准备用户、两个骑手、区域管理员和超级管理员账号。完成微信沙箱支付退款、余额支付退款、两个骑手并发抢同单、骑手送达后用户确认、24 小时任务人工缩短验证、申诉冻结、退款后结算排除和已结算冲正。

微信开发者工具及真机必须分别验证弱网、重复点击、退出重进、订阅消息拒绝、定位关闭和支付取消。压测至少覆盖同一订单 50 个并发接单请求，只允许一个成功且只生成一个接单节点。

## 14. 完成定义

只有同时满足以下条件才可称为跑腿闭环完成：

1. 订单金额只能由服务端计算并可审计还原；
2. 骑手不能直接完成订单；
3. 用户确认和无争议自动确认均可执行；
4. 微信、余额和零元订单退款各自闭环；
5. 申诉会冻结自动确认和结算，处理结果能驱动资金动作；
6. 每个结算金额能追溯到唯一订单，退款可撤销或冲正；
7. 接单前隐私脱敏、位置授权和区域权限经过回归验证；
8. 后台不能绕过领域状态机；
9. 自动化测试、真实数据库并发、微信沙箱和小程序真机证据齐全；
10. 部署、灰度和监控完成后，才标记“已上线验证”，本地构建或单测通过只标记“本地已验证”。
