## 0. 这份文档怎么使用

这是一份长期接力总纲。后续任何开发会话开始前，先阅读本文件，再阅读对应阶段的详细实施计划。它用于防止上下文增多后偏离目标、重复设计或把局部页面优化误当成全链路完成。

每轮工作必须先回答五个问题：

1. 当前正在执行哪个阶段、哪个任务编号？
2. 本轮允许修改哪些代码根目录和文件？
3. 本轮是否涉及数据库、真实资金、外部服务或线上环境？
4. 通过条件是什么，哪些证据仍未取得？
5. 出现失败时如何停止、回滚或恢复？

除非用户明确改变方向，本文的产品边界、角色定义、资金规则和证据标准持续有效。

## 1. 总目标

把现有外卖功能从“散落在小程序、后台和骑手模块里的页面与接口”，升级为一套由四个角色端共同使用的本地生活外卖操作系统：

- 用户能快速、准确、可预期地下单和跟踪履约；
- 商户能独立完成门店、员工、商品、订单、售后、设备和财务经营；
- 骑手能稳定完成抢单、取货、送达、异常、收入和结算；
- 平台管理员能按总部、区域、站点管理准入、履约、营销、资金和风险；
- Node/NestJS 后端在高并发和局部故障下不重复记账、不重复抢单、不无限等待，并能水平扩容和优雅降级。

“不能宕机”不作为绝对承诺。工程目标是消除单点、快速故障摘除、核心交易幂等、状态可恢复、发布可回滚、故障可观测。

## 2. 产品与工程范围

### 2.1 本项目包含

1. 平台超级管理员与受限区域管理员后台；
2. 独立商户 Web 操作网站；
3. 用户小程序中的正常外卖板块；

6. 高并发、幂等、队列、高可用、压测和灰度发布能力。

### 2.2 本轮明确不包含

- 宿舍小店；
- 未经授权的真实银行卡、支付宝或微信自动打款；
- 未备份、未 dry-run 的生产数据库迁移；
- 仅为了“看起来完整”而创建没有后端能力的空菜单或假页面；
- 复制外部平台代码、品牌素材或私有交互实现。

BoolC、Keloop 只作为角色分端、菜单组织、经营闭环和异常处理的参考，不作为代码或视觉资产来源。

## 4. 总体架构原则

### 4.1 一个业务中心，四个角色端

不得为商户网站、骑手端或管理后台分别复制订单、支付、退款和结算逻辑。四端通过不同接口边界调用同一个业务中心：

```text
用户小程序  ─┐
商户 Web    ─┼─> 统一 NestJS 业务中心 ─> PostgreSQL / Redis / 对象存储
骑手端      ─┤                         ├> 事务 Outbox / 持久队列 / Worker
平台后台    ─┘                         └> WebSocket / 通知 / 打印 / 监控
```

### 4.2 服务端是唯一信任边界

- 前端隐藏菜单和按钮只改善体验，不替代权限校验；
- 金额、库存、优惠、距离、订单状态和可执行动作由服务端重新计算；
- 所有关键写操作使用数据库事务、唯一键、幂等键或状态版本；
- 所有角色数据必须同时满足身份、组织、门店、区域和业务权限范围。

### 4.3 不展示空能力

后台和商户网站只有在接口、权限、加载/空/错状态及核心操作均可用时，才加入正式菜单。禁止先摆菜单再长期显示“开发中”。

### 4.4 资金事实不可覆盖

资金变化写入不可变账务行；退款、补偿和纠错通过新冲正行完成。结算锁定账务行，而不是每次从订单重新统计。真实打款必须有账户快照、尝试记录、复核、回单和幂等状态。

### 4.5 证据分层

源码、单元测试、本地数据库、浏览器/模拟器、真机、部署、真实支付/退款和压力测试是不同证据。任一层通过都不能替代其他层。

## 5. 四端产品蓝图

## 5.1 平台超级管理员后台

### 目标

让平台人员围绕待办和异常工作，而不是在几十个列表里寻找问题；同时保证总部、区域、站点数据范围严格隔离。

### 主菜单

1. **运营总览**
   - 今日经营指标
   - 待审核、待退款、超时、无人接单、打印故障、资金差异
2. **外卖中心**
   - 外卖工作台
   - 商户组织与门店
   - 商户入驻审核
   - 商户账号与权限
   - 商品与门店分类
   - 订单履约
   - 配送调度
   - 售后与评价
   - 打印与设备
3. **营销中心**
   - 平台活动
   - 区域活动
   - 商户报名与出资
   - 优惠券和预算
4. **财务中心**
   - 商户账务
   - 结算单
   - 收款账户审核
   - 打款与复核
   - 骑手结算
   - 资金异常
5. **风控与审计**
   - 高风险操作
   - 权限变更
   - 资金调整
   - 异常修复记录

### 管理员规则

- 超级管理员可以查看全局，但敏感资金操作仍受双人复核；
- 区域管理员只能操作授权区域；
- 商户、订单、骑手、财务接口均必须显式传入操作者，由统一数据范围服务构造查询条件；
- 仪表盘使用数据库聚合或经营事实表，不能循环查询全部区域和全量订单。

## 5.2 独立商户 Web

### 技术形态

复用现有 Vue 3、Pinia、Vue Router、Element Plus 工程，在同一构建产物中建立 `/merchant-console` 独立入口。它拥有：

- 独立商户登录页；
- 独立 Token、刷新 Token 和存储键；
- 独立 Axios 客户端；
- 独立路由守卫；
- 独立布局和菜单；
- 独立门店选择状态；
- 不读取管理员登录状态，不显示管理员菜单。

如果未来访问量、发布节奏或品牌要求需要，再把这套入口拆成单独前端包；第一期不重复维护两套组件库和构建链。

### 商户主菜单

1. 今日工作台
2. 订单中心
3. 商品与库存
4. 门店设置
5. 员工与权限
6. 营销活动
7. 财务中心
8. 打印与设备

菜单按阶段上线，未完成能力不展示。

### 商户关键体验

- 顶部始终显示当前门店，多门店切换后所有请求取消并重新加载；
- 今日工作台突出新订单、待接单、即将超时、退款、缺货和设备异常；
- 接单、拒单、备餐、出餐等操作有操作锁和最新状态冲突提示；
- 商品、分类、库存全部属于当前门店；
- 财务金额逐笔可解释，状态区分“核算完成”“打款处理中”“已到账”；
- 收款账号仅显示脱敏值，不进入浏览器本地存储、通用日志或导出。

## 5.3 用户小程序外卖板块

### 核心链路

定位/选区域 → 服务端搜索排序 → 商户详情 → 商品与购物车 → 结算校验 → 支付 → 商户接单 → 骑手履约 → 用户确认 → 评价/售后。

### 必须修正

- 搜索、综合排序、销量排序、距离排序在服务端完成，禁止每页前端排序；
- 未选择区域时明确引导，不静默使用固定区域；
- 坐标无效时展示“距离暂不可用”，不能显示 0 米或默认城市位置；
- 打烊但支持预约的门店允许进入选品，并显示最早送达时间；
- 订单状态通过 WebSocket/事件推送更新，低频刷新只做兜底；
- 费用、优惠出资方、配送预计时间、退款状态和申诉入口清楚一致；
- 本项目不修改宿舍小店链路。

## 5.4 官方骑手端

### 核心链路

登录/审核 → 上线 → 统一任务池 → 接单 → 导航到店 → 到店/取货 → 导航送达 → 到达 → 用户确认/系统确认 → 收入与结算。

### 必须修正

- 外卖配送和跑腿统一为 `DeliveryTask` 读模型或至少统一游标，避免双数据源分页漏单；
- 忙碌状态仍属于在线工作，不能显示成离线；
- 有进行中任务时隐藏或禁用抢单池，并解释原因；
- 接单卡展示距离、预计耗时、送达期限、重量/件数、楼层和收入构成；
- 工作台改为聚合接口，避免一次刷新触发多个重查询；
- 收入、奖励、处罚、结算、提现和申诉覆盖所有真实配送来源；
- 骑手只能推进到已到达，用户或系统确认完成后才进入可结算状态；
- 继续保留官方骑手服务端校验、弱网定位队列、异常凭证和接单并发保护。

## 6. 第一实施里程碑：商户身份、权限、网站框架与后台入口

### 6.1 里程碑目标

建立今后所有商户订单、商品、营销和财务能力共同使用的身份与门店权限底座，并提供真实可登录、可切换门店、可管理员工的商户网站骨架和平台管理入口。

### 6.2 数据模型

#### `MerchantOrganization`

代表一个经营主体，而不是单个门店。第一期字段固定为：

- `id`
- `name`
- `status`: active/suspended/closed
- `ownerUserId`
- `createdAt`、`updatedAt`

现有 `Merchant` 继续代表门店，增加 `organizationId`。一个组织可以有多个门店。

#### `MerchantMember`

代表用户在经营主体中的成员身份：

- `id`
- `organizationId`
- `userId`
- `status`: active/disabled
- `sessionVersion`
- `invitedBy`
- `createdAt`、`updatedAt`
- 唯一约束：`organizationId + userId`

#### `MerchantMemberStoreRole`

代表成员在具体门店的内置角色：

- `id`
- `memberId`
- `merchantId`
- `roleKey`: owner/manager/order_clerk/product_clerk/finance
- `createdAt`、`updatedAt`
- 唯一约束：`memberId + merchantId + roleKey`

第一期不建立自定义角色编辑器。权限点在代码与共享合同中定义，后续允许自定义角色时只新增角色模板和权限绑定，不改变接口数据范围。

#### 门店分类归属

现有 `Category` 增加明确作用域：

- `scopeType`: platform/store
- `merchantId`: 门店分类必填，平台模板为空
- 门店分类写操作必须校验当前商户权限
- 旧分类迁移为平台模板，迁移前生成影响报告

### 6.3 五种商户角色

| 能力 | 店主 | 店长 | 订单员 | 商品员 | 财务员 |
|---|---:|---:|---:|---:|---:|
| 查看门店工作台 | 是 | 是 | 是 | 是 | 是 |
| 接单/拒单/备餐/出餐 | 是 | 是 | 是 | 否 | 否 |
| 处理退款申请 | 是 | 是 | 是 | 否 | 查看 |
| 商品/规格/分类/库存 | 是 | 是 | 否 | 是 | 否 |
| 营业时间/配送/打印 | 是 | 是 | 部分 | 部分 | 否 |
| 普通员工管理 | 是 | 是 | 否 | 否 | 否 |
| 修改店主或财务角色 | 是 | 否 | 否 | 否 | 否 |
| 查看资金与结算 | 是 | 否 | 否 | 否 | 是 |
| 确认结算/发起异议 | 是 | 否 | 否 | 否 | 是 |
| 新增或更换收款账户 | 是 | 否 | 否 | 否 | 否 |

后端返回 `allowedActions`；前端根据它展示操作，但每次写请求仍由后端重新校验。

### 6.4 后端模块

#### `MerchantIdentityModule`

负责组织、成员、角色、邀请、停用和商户会话。

#### `MerchantAccessService`

统一实现：

```text
用户身份
  -> 商户成员是否有效
  -> 门店是否属于同一组织
  -> 门店和组织是否可用
  -> 是否拥有目标权限
  -> 返回规范化访问上下文
```

控制器和业务服务不得各自复制所有权判断。所有商户写接口必须从访问上下文取得 `merchantId`，不能信任 DTO 自报归属。

#### 商户认证

建议专用接口：

- `POST /merchant-web/auth/phone/send-code`
- `POST /merchant-web/auth/phone/login`
- `POST /merchant-web/auth/refresh`
- `POST /merchant-web/auth/logout`
- `GET /merchant-web/session`
- `GET /merchant-web/shops`

商户访问令牌使用独立 `audience=merchant_web`；管理员令牌、用户小程序令牌和商户令牌不得混用。令牌中只放稳定身份和会话版本，不把客户端可篡改的当前门店当作最终权限事实。

#### 商户成员接口

- `GET /merchant-web/shops/:merchantId/members`
- `POST /merchant-web/shops/:merchantId/members`
- `PUT /merchant-web/shops/:merchantId/members/:memberId/roles`
- `PUT /merchant-web/shops/:merchantId/members/:memberId/status`

#### 平台管理接口

- `GET /admin/merchant-organizations`
- `GET /admin/merchant-organizations/:id`
- `GET /admin/merchant-organizations/:id/shops`
- `GET /admin/merchant-organizations/:id/members`
- `POST /admin/merchant-organizations/:id/owner-recovery`
- `PUT /admin/merchant-members/:id/status`
- `GET /admin/merchant-portal/status`

后台接口继续使用管理员权限和区域数据范围；超级管理员也不能绕过资金复核规则。

### 6.5 商户 Web 第一批页面

1. **商户登录**：手机号、验证码、协议、错误状态和会话过期；
2. **门店选择**：只展示有有效角色的门店；
3. **今日工作台骨架**：门店状态、角色、待办摘要和后续入口，不伪造经营数据；
4. **员工与权限**：新增成员、分配内置角色、停用、查看审计；
5. **门店资料**：只展示和编辑当前已有可靠后端字段；
6. **退出与会话管理**：清理所有商户端本地状态。

### 6.6 平台后台第一批页面和菜单

在现有“外卖中心”中新增并显式展示：

- 商户组织与门店；
- 商户账号与权限；
- 商户入口状态。

原有商户列表、审核、商品、订单、售后、评价、打印等菜单保留并重新归类。新增菜单必须同时具备路由、权限映射、页面加载/空/错状态和真实接口。

### 6.7 数据迁移

1. 新增表、字段和索引，默认不影响旧接口；
2. dry-run 统计现有 `Merchant.userId` 的有效、空值、重复、多店情况；
3. 每个有效店主建立组织、成员和 owner 角色；
4. 同一用户的多门店默认归入一个组织，但名称和经营主体冲突时进入人工核对列表；
5. 迁移只追加关系，不删除 `Merchant.userId`；
6. 双读核对通过后，旧字段改为兼容只读；
7. 正式迁移前备份目标数据库并记录恢复点；
8. 所有写入脚本默认 dry-run，只有显式 `--apply` 才能修改数据。

### 6.8 错误与冲突处理

- `401`：商户会话失效，清理商户 Token，跳转商户登录；
- `403`：明确显示无当前门店权限，不能伪装成空列表；
- `404`：资源不存在或不在可见范围，响应不泄露其他商户信息；
- `409`：成员角色、库存、订单或状态版本冲突，返回最新版本；
- `422`：字段级业务校验；
- `429`：登录、导出、邀请和高频写操作限流；
- `503`：数据库、Redis 或关键依赖不可用时快速失败和降级，不无限等待。

所有商户敏感操作写审计：操作者、组织、门店、目标成员、变更前后值、原因、请求 ID、时间和结果。

### 6.9 第一里程碑验收

- 五种角色的权限矩阵数据驱动测试通过；
- 跨组织、跨门店、被停用成员全部拒绝；
- 管理员 Token、普通用户 Token、商户 Token 无法互相冒用；
- 角色变化或停用后旧会话按 `sessionVersion` 失效；
- 三套 Prisma Schema 结构一致；
- 迁移 dry-run 能输出数量、冲突和计划写入行；
- 后端构建、相关测试、管理员后台构建通过或准确隔离既有无关错误；
- 浏览器完成店主登录、多店切换、创建员工、修改角色、越权拒绝和退出；
- 管理后台能看到并操作三个新增商户菜单；
- 本里程碑不执行生产迁移、不写真实资金、不发布线上。

## 11. 第六实施里程碑：高并发、高可用和生产化

### 11.1 目标拓扑

```text
小程序/商户/骑手/后台
        |
    WAF + 负载均衡 + 边缘限流
        |---------------------|
无状态 Nest API x2+      WebSocket x2+
        |                    |
    PgBouncer           Redis Pub/Sub
        |                    |
PostgreSQL 高可用       Redis 高可用
        |
事务 Outbox -> 持久队列 -> Worker xN -> 打印/短信/推送/退款回查/对账

所有节点 -> 指标、日志、链路追踪、告警
```

### 11.2 必做能力

- `enableShutdownHooks`、SIGTERM 排水、WebSocket 连接迁移/重连；
- liveness 与 readiness 分离，readiness 检查数据库、Redis 和关键队列；
- API/WS 无状态水平扩容；
- Redis 锁使用随机令牌、Lua 校验释放和必要续租；
- 支付、退款、抢单、结算使用数据库唯一键和 CAS，Redis 只做加速；
- Outbox 保证数据库事实提交后事件可重放；
- 打印、通知、回查、对账由 Worker 执行；
- 全局与角色级限流、连接限制、超时、熔断和背压；
- Prisma 连接池参数、PgBouncer、慢查询和复合索引；
- 日志不写敏感数据，错误和请求日志采样不能拖垮业务数据库；
- 监控事件循环延迟、连接池占用、队列积压、WebSocket 在线数、重复冲突、订单错误率和资金差异。

### 11.3 建议生产验收目标

目标值需按实际峰值和机器规格校准，初始建议：

- API 可用性目标 99.95%；
- 常用读取 p95 小于 300ms，核心写入 p95 小于 500ms；
- 重复支付、重复退款、重复抢单和重复结算为 0；
- 单 API 节点、单 Worker 或单 WebSocket 节点退出不影响核心交易；
- 队列积压、数据库连接耗尽、Redis 故障和第三方超时均有告警与降级；
- 发布可灰度、可停止、可回滚，不在高峰直接全量替换。

## 20. 禁止出现的错误完成声明

- 只有菜单，没有接口或权限；
- 只有页面截图，没有真实交互；
- 只有接口单测，没有浏览器/真机验证；
