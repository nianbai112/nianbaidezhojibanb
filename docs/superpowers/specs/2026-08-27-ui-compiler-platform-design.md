## 1. 决策

把现有“若干固定组件的页面装修器”升级为一套可持续扩展的小程序 UI 编译平台。

平台采用以下已确认决策：

1. **受控自由**：运营人员可以自由布局、嵌套、换肤、增删组件、配置已注册数据源和动作；不能下发任意 JavaScript、WXML、接口地址或无限制 CSS。
2. **自有内核**：灵萌掌握统一页面协议、组件注册协议、校验、编译、发布和运行时。TMagic、VTJ 等只允许作为可替换的编辑器适配层，不能成为线上协议的唯一来源。
3. **双发布链路**：核心页面和主业务流程由后台生成代码包；运营位和活动页使用安全动态渲染。
4. **统一协议**：原生编译与动态渲染都消费 `PageDocument v2`，不再为后台预览、代码包和小程序运行时分别维护互不兼容的数据模型。
5. **模板化增量编译**：核心页面使用固定模板骨架、组件片段编译和内容哈希缓存，不从零手写整页源码，也不在第一期引入通用模板引擎。
6. **渐进迁移**：新平台与现有页面并行，先迁移活动页和首页运营位，再迁移核心页面；任何阶段都必须保留旧版本和回退能力。

## 2. 当前事实与问题

当前仓库同时存在 `UiEditor`、`RealTimeEditor`、`DesignerStudio`、`ActivityStudio`、`TmagicPageEditor`、`LayoutBuilder` 以及首页、消息页、个人中心专用编辑器。

现有协议主要是扁平的：

```json
{
  "components": [
    {
      "id": "banner",
      "type": "banner",
      "enabled": true,
      "order": 0,
      "config": {},
      "style": {}
    }
  ],
  "settings": {}
}
```

它存在以下结构性限制：

- 组件不能形成真正的容器树，难以实现自由组合、栅格和嵌套布局。
- 组件定义、后台预览和小程序渲染逻辑分散在多处；新增组件需要同步修改多个大文件。
- 后台预览与小程序运行时存在手工复刻，容易产生表现差异。
- 部分保存、发布、写代码包和动态下发语义曾经混合，运营人员难以判断哪一步影响线上。
- 当前代码包服务主要写入布局 JSON 和 `bundled.js`，尚未形成真正的 WXML/WXSS/JS/JSON 原生页面编译器。
- TMagic 活动页运行时只识别少量节点，不能承担整个小程序的统一页面协议。
- 动态业务模块大量依赖占位和宿主插槽，无法仅靠继续增加 `if/elif` 分支演化成开放组件平台。

本设计保留现有可用能力，但不继续扩大这些并行模型。

## 3. 目标

### 3.1 产品目标

- 运营人员可以通过拖拽和配置，定制小程序的页面结构、样式、主题、内容、运营模块和已注册业务模块。
- 活动页和运营位可以不提交微信审核即时发布。
- 首页、消息、个人中心、发布、订单、登录、支付等核心页面保持原生代码包稳定性。
- 组件库能够持续扩充；新增普通组件不需要修改编辑器核心。
- 草稿、预览、审核、发布、灰度、回滚具有清楚且互相隔离的语义。
- 多校区可以继承全局模板，并在允许的范围内覆盖运营内容。

### 3.2 工程目标

- 建立版本化的 `PageDocument v2` 和组件注册合同。
- 建立后台预览、后端校验、原生编译、动态渲染共享的组件语义。
- 建立确定性、可缓存、可测试、可审计的编译产物。
- 建立动态页面能力协商，避免旧版小程序遇到新组件时整页崩溃。
- 编译或发布失败时不覆盖现有线上版本或本地有效代码包。
- 用迁移器读取现有扁平布局，不要求一次性重做已有页面。

## 4. 非目标

- 不允许后台编写或下发任意 JavaScript、WXML、WXSS、SQL 或接口 URL。
- 不把支付、订单状态机、登录凭据、消息会话和权限判断改造成运营配置。
- 不在第一期开发浏览器级脚本语言、任意表达式引擎或通用工作流引擎。
- 不在第一期追求几百个组件；先建立可扩展内核和约 30 个高价值组件。
- 不直接把 VTJ、TMagic 或其他开源项目的 DSL 作为灵萌永久存储协议。
- 不在后台点击“保存草稿”时修改小程序源码目录、生成线上版本或发布动态配置。
- 不把本地构建通过等同于微信审核、真机验证或线上发布完成。

## 5. 方案选择

### 5.1 采用：自有内核与可替换设计器

```text
可视化编辑器
    -> 组件注册中心
    -> PageDocument v2
    -> 校验与安全策略
    -> 原生编译发布 / 动态快照发布
    -> 小程序原生宿主 / 动态运行时
```

灵萌拥有协议和发布链。编辑器画布通过适配器消费组件注册信息。第一期可以复用当前 Vue 编辑器、Element Plus、TMagic 中仍有价值的画布能力；后续可以评估 VTJ 适配器，但更换编辑器不能改变已保存页面和小程序运行合同。

### 5.2 不采用：继续扩展现有 TMagic DSL

它能加快活动画布试验，但当前运行时能力、绝对定位模型和小程序业务组件接入方式不足以承担整个小程序。继续把业务协议绑在 TMagic 上，会把迁移成本推迟而不是消除。

### 5.3 不采用：全面替换成 VTJ

VTJ 可以作为编辑体验和 DSL 设计参考，但直接替换现有编译小程序树、业务页面和运行时风险过高。平台首先稳定自己的合同，再决定是否引入设计器适配层。

## 6. 总体架构

```text
┌────────────────────────────────────────────────────┐
│                    管理后台                         │
│  组件库 / 图层树 / 画布 / 属性 / 样式 / 数据 / 动作 │
└───────────────────────┬────────────────────────────┘
                        │ PageDocument v2
┌───────────────────────▼────────────────────────────┐
│                UI Compiler Backend                 │
│  Schema迁移 │ Registry │ Validator │ Versioning    │
│  Preview    │ Compiler │ Dynamic Publisher         │
└──────────────────┬───────────────────┬──────────────┘
                   │                   │
          核心页面构建版本      动态不可变快照
                   │                   │
┌──────────────────▼─────────┐ ┌──────▼──────────────┐
│ 原生页面宿主 + 生成片段    │ │ 动态页面壳/运营插槽 │
│ WXML/WXSS/JS/JSON          │ │ 安全运行时 + 缓存   │
└────────────────────────────┘ └─────────────────────┘
```

系统拆成七个明确单元：

1. **UI Studio**：编辑页面，不决定线上运行方式。
2. **PageDocument Contract**：保存页面语义，不保存某个编辑器的内部状态。
3. **Component Registry**：定义组件可编辑、可编译、可动态渲染的能力。
4. **Validator**：执行结构、能力、安全、平台和性能检查。
5. **Native Compiler**：生成核心页面的原生代码片段和构建清单。
6. **Dynamic Publisher**：发布运营位和活动页不可变快照。
7. **Mini Program Runtime**：加载已发布动态快照，执行允许的数据和动作适配器，并负责缓存与降级。

## 7. PageDocument v2

### 7.1 顶层合同

```json
{
  "schemaVersion": 2,
  "id": "home-global",
  "revision": 12,
  "page": {
    "key": "home",
    "title": "首页",
    "releaseMode": "mixed",
    "layoutMode": "flow",
    "theme": "campus-green",
    "regionId": "global"
  },
  "root": {
    "id": "root",
    "type": "page",
    "props": {},
    "style": {},
    "layout": {
      "display": "flex",
      "direction": "column",
      "gap": 0
    },
    "children": []
  },
  "settings": {},
  "metadata": {
    "createdBy": "admin-id",
    "updatedAt": "2026-08-27T00:00:00.000Z"
  }
}
```

`releaseMode` 只有三种值：

- `compiled`：整个可编辑结构进入代码包。
- `dynamic`：整个文档由动态页面壳加载。
- `mixed`：核心结构进入代码包，文档内含一个或多个动态运营插槽。

### 7.2 节点合同

```json
{
  "id": "banner_1",
  "type": "banner",
  "componentVersion": 1,
  "enabled": true,
  "props": {
    "height": 280,
    "autoplay": true
  },
  "style": {
    "margin": [0, 24, 16, 24],
    "borderRadius": "{radius.lg}"
  },
  "layout": {},
  "bindings": {
    "items": {
      "source": "operations.homeBanners",
      "params": {
        "regionId": "$context.regionId"
      }
    }
  },
  "actions": {
    "itemClick": {
      "type": "navigate",
      "target": "$event.item.link"
    }
  },
  "visibility": {
    "when": "authenticated"
  },
  "children": []
}
```

### 7.3 合同规则

- 所有节点必须有页面内唯一且稳定的 `id`。
- 节点树有最大深度、最大节点数和容器子节点限制。
- `props`、`style`、`bindings`、`actions` 必须通过组件注册合同校验。
- `children` 只允许出现在声明了插槽能力的组件上。
- 文档不能保存函数、循环引用、二进制数据或任意代码字符串。
- JSON 序列化必须确定化；对象键排序和默认值归一化后才能计算构建哈希。
- `metadata` 不参与运行时语义哈希，避免只修改时间或备注触发重编译。

### 7.4 旧协议迁移

`v1 -> v2` 迁移器执行以下确定性转换：

- `components` 按 `order` 排序后成为 `root.children`。
- `config` 转成 `props`。
- 旧 `style` 转成受支持的 v2 样式字段。
- `enabled`、组件 `id` 和页面 `settings` 保留。
- 旧 `tmagic-page` 转成受控的 `legacy-activity` 节点，迁移期继续可读；重新编辑时提示转换为新活动文档。
- 未知组件保留原始数据并标记 `migrationError`，不能静默丢弃或发布。

迁移在读取时可以预览，但只有管理员保存 v2 草稿后才写回；原 v1 已发布版本保持不可变。

## 8. 组件注册协议

### 8.1 注册内容

每个组件注册包提供：

| 字段 | 职责 |
|---|---|
| `manifest` | 类型、名称、分类、版本、图标、适用页面 |
| `propsSchema` | 默认值、字段类型、约束和属性面板 |
| `slots` | 插槽名称、允许的子组件、数量和深度 |
| `editorPreview` | 后台画布渲染 |
| `compiledAdapter` | 原生代码片段和依赖声明 |
| `dynamicAdapter` | 小程序动态模板和数据归一化 |
| `dataSources` | 该组件允许绑定的数据源 |
| `actions` | 该组件允许触发的动作 |
| `migrations` | 组件配置版本迁移 |

示意合同：

```ts
interface ComponentManifest {
  type: string
  version: number
  category: 'layout' | 'base' | 'display' | 'form' | 'business'
  targets: {
    compiled: boolean
    dynamic: boolean
  }
  layoutModes: Array<'flow' | 'grid' | 'absolute'>
  minRuntimeVersion?: number
  propsSchema: Record<string, unknown>
  slots?: Array<{
    name: string
    accepts: string[]
    min?: number
    max?: number
  }>
}
```

### 8.2 单一语义来源

组件属性、默认值、约束、目标能力和版本只能在注册合同中定义一次。后台属性面板、后端校验器、编译器和运行时清单从同一合同生成或读取，禁止再维护四份手写枚举。

编辑预览、原生组件和动态模板是平台差异实现，但必须通过同一组组件契约用例。

### 8.3 动态能力协商

动态页面只能使用当前小程序代码包已经内置的组件和数据适配器。动态快照包含：

- `schemaVersion`
- `runtimeVersion`
- 使用的组件类型和版本
- 文档内容哈希
- 发布时间和发布版本

客户端遇到高于自身能力的组件时：

1. 单个非关键组件使用注册的降级视图或隐藏。
2. 必需组件不兼容时拒绝激活新快照，继续使用最近一次有效缓存。
3. 记录可诊断错误，但不让整个核心页面崩溃。

因此“新增组件”仍需要先发布包含该组件运行时的小程序代码包；代码包具备组件后，运营人员可以无限创建和调整使用这些组件的动态页面，无需再次提审。

## 9. 布局、样式与主题

### 9.1 布局模式

- 核心页面默认使用 `flow`、Flex 和 Grid，保证不同设备宽度、字体和安全区下稳定。
- 活动页可以使用 `absolute` 自由画布，但节点位置仍使用受限数值和 750rpx 设计坐标。
- 容器可以嵌套；普通叶子组件不能拥有子节点。
- 吸顶、横向滚动和固定底栏作为受控布局组件提供，不允许任意 `position: fixed`。

### 9.2 样式白名单

允许的样式以结构化字段保存，包括尺寸、间距、Flex/Grid、背景、边框、圆角、阴影、字体、对齐、透明度和有限定位字段。

禁止保存完整 CSS 字符串、选择器、`url(javascript:)`、表达式、任意动画代码或可以突破页面边界的未知属性。

### 9.3 设计令牌

主题至少包含：

- 品牌色、语义色、背景和文字色
- 字号、字重和行高
- 间距阶梯
- 圆角阶梯
- 阴影阶梯
- 安全区和页面最大宽度

节点可以引用 `{color.primary}`、`{space.4}`、`{radius.lg}` 等令牌。全局主题、页面覆盖和节点覆盖按明确优先级合并；发布时解析未知令牌为错误，不静默输出无效样式。

## 10. 数据源、动作与可见性

### 10.1 数据源注册

后台只展示注册的数据源，例如：

- `operations.homeBanners`
- `content.feed`
- `merchant.recommendedList`
- `user.profileSummary`
- `order.recentOrders`

每个数据源声明输入参数、输出结构、缓存、认证要求、超时、空态和可用页面。PageDocument 只保存 `source` 和结构化 `params`，不保存 URL、请求头或 Token。

编译运行时和动态运行时通过同名适配器调用现有 `lmapi` 或宿主页面数据，不复制业务接口实现。

### 10.2 动作注册

首期动作包括：

- 页面跳转、重定向、切换 Tab、返回
- 打开已允许的网页或其他小程序
- 预览图片、复制、电话、地图
- 打开发布弹窗
- 领取已注册优惠券
- 提交已注册表单
- 调用组件内部的安全业务动作

动作参数使用受限 JSON Path 引用 `$context`、`$event`、`$item` 和组件状态。禁止 `eval`、函数表达式、任意方法名和动态接口地址。

### 10.3 可见性

第一期只支持枚举式条件，如登录状态、审核模式、校区、用户角色和功能开关。多个条件使用结构化 `all/any/not` 组合，不实现通用表达式语言。

安全条件仍由服务端和业务页面复核；隐藏组件不能替代权限控制。

## 11. 后台编辑器体验

编辑器采用三栏工作台：

```text
组件库 / 图层树 | 手机画布 | 属性 / 样式 / 数据 / 动作
```

第一期包含：

- 拖拽新增、排序、容器嵌套和跨容器移动。
- 图层树、节点面包屑、复制粘贴、删除、撤销重做。
- 多选、对齐、等间距和组合操作。
- 页面模板、区块模板和保存为复用区块。
- 全局主题、页面样式和组件样式三级编辑。
- 常见手机尺寸、安全区、吸顶和固定底栏预览。
- 模拟数据、空数据、加载和失败状态预览。
- 草稿自动保存、手动保存、版本备注、发布差异和发布检查。
- PageDocument JSON 只读查看和受校验导入，不提供任意代码编辑器。

画布状态和 PageDocument 状态分离。撤销历史、选中节点、缩放比例、面板开关等编辑器临时状态不得写入页面协议。

## 12. 原生编译器

### 12.1 编译边界

核心页面保留手写的生命周期、权限、请求、支付和状态机逻辑。编译器只负责生成 UI 结构、样式、静态配置、组件依赖和事件桥接描述。

每个核心页面使用稳定宿主合同：

- 宿主 JS 提供已注册数据和动作。
- 宿主 WXML 只在固定位置包含生成片段。
- 生成片段只能引用注册过的原生组件、数据键和动作事件。
- 编译器不得覆盖手写业务文件中的非生成区域。

### 12.2 固定模板

预置以下模板：

```text
templates/page.template.wxml
templates/page.template.wxss
templates/page.template.js
templates/page.template.json
```

模板使用不会与 WXML 冲突的严格标记：

```xml
<!-- @ui:imports -->

<view class="ui-page">
  <!-- @ui:page-body -->
</view>
```

编译器递归处理 PageDocument 节点，得到：

- `imports`
- `pageBody`
- `pageStyles`
- `pageData`
- `usingComponents`
- `actionBindings`

然后执行精确占位符替换。每个必需占位符必须恰好出现一次；缺失或重复都视为模板错误并停止构建。

第一期不使用 Handlebars，因为其 `{{ }}` 与 WXML 插值冲突；也不引入 EJS。将来固定插槽不足以表达模板时，再单独评估并把 EJS 作为直接依赖引入，不能依赖 `@nestjs/schematics` 间接安装的 Handlebars。

### 12.3 安全生成

- 用户文本、图片和普通配置主要进入生成的数据模块，通过 WXML 数据绑定传递。
- 组件类型、标签名、属性名和文件路径只能来自注册合同。
- 所有字符串按目标文件类型转义，禁止把原始输入直接拼入 WXML、JS 或 JSON。
- 生成文件包含“自动生成，请勿手改”和来源版本信息。
- 编译输出经过 JSON 解析、JavaScript 语法、WXML 结构、WXSS 白名单和路径沙盒检查。

### 12.4 增量构建

页面构建哈希由以下确定化输入计算：

```text
规范化 PageDocument
+ 使用的组件及编译适配器版本
+ 页面模板版本
+ 主题令牌版本
+ 编译器版本
= buildHash
```

哈希未变化时复用已有构建结果。组件编译适配器升级时，只重编译实际使用该组件的页面。

### 12.5 隔离与原子提升

构建默认不直接写 `/Users/nianbaidediannao/Desktop/前端文件`：

1. 从受信任的小程序基线创建隔离构建工作区。
2. 在临时目录生成和覆盖明确的生成文件。
3. 运行校验、测试和包体积检查。
4. 成功后把完整目录原子提升为不可变构建版本。
5. 管理员可以下载 ZIP，或执行单独、明确的“应用到本地源码”操作。

保存草稿、动态发布和生成代码包是三个不同动作。任何失败都不能留下半生成页面或覆盖上一个可用构建。

### 12.6 构建清单

每个构建版本记录：

- `buildId`、`buildHash`、创建时间和操作者
- PageDocument 版本
- 编译器、模板、主题和组件版本
- 新增、修改和删除的生成文件
- `app.json` 与分包变化
- 包体积及各分包体积
- 校验、测试和微信开发者工具检查结果
- 来源基线标识和可回滚构建版本

## 13. 动态发布与小程序运行时

### 13.1 两种动态承载

1. **运营插槽**：核心页面代码包内预置 `dynamic-slot`，用于首页楼层、广告、弹窗和专题入口。
2. **活动页面壳**：固定路由按 `slug` 加载完整动态文档，例如 `/pages/operations/page?slug=welcome-2026`。

### 13.2 动态发布流程

```text
草稿
  -> PageDocument结构校验
  -> 动态组件与动作白名单校验
  -> 运行时版本兼容检查
  -> 预览
  -> 不可变发布快照
  -> 按校区激活
```

动态发布只改变服务端当前发布指针，不修改小程序代码包。第一期灰度以校区为单位；不实现复杂的用户百分比分流。

### 13.3 客户端读取与缓存

公开响应包含版本、运行时要求、内容哈希和文档。服务端支持 `ETag` 或等价版本协商。

客户端处理顺序：

```text
最新兼容且校验通过的远程版本
  -> 最近一次有效本地缓存
  -> 代码包内置默认版本
  -> 安全空态
```

只有完整解析、能力兼容和内容哈希验证通过的响应才能替换本地有效缓存。网络失败、JSON 损坏、未知必需组件或超时不会清除旧缓存。

### 13.4 动态渲染器扩展

动态运行时不继续维护单个巨型 `if/elif` 文件。构建小程序代码包时，根据组件注册表生成：

- WXML 模板导入清单
- 动态组件类型映射
- 数据归一化映射
- 动作映射
- 运行时能力清单

注册新动态组件需要重新生成并提交一次运行时代码包，但之后页面使用和配置该组件无需重新提审。

## 14. 版本、存储与接口语义

### 14.1 版本状态

页面版本具有以下状态语义：

- `draft`：后台可编辑，不对小程序公开。
- `validated`：通过当前合同检查，可预览但未发布。
- `published`：当前动态线上版本或当前构建来源版本。
- `archived`：不可变历史版本，可选择回滚。
- `rejected`：校验或审核未通过，保留诊断结果。

### 14.2 现有数据兼容

第一期复用现有 `Config` 草稿/发布指针和 `LayoutVersion` 历史能力，不为组件注册表新建数据库表。组件注册表由代码版本管理。

`LayoutVersion` 在实施时允许增加可选元数据，如 `schemaVersion`、`releaseMode`、`buildHash` 和 `artifactManifest`；具体数据库变更必须走三份 Prisma schema 同步和 additive migration，不能直接重建生产表。

### 14.3 接口边界

现有 `/admin/layout/*` 和 `/layout/*` 在迁移期间继续服务 v1 页面。v2 接口应显式区分：

- 读取和保存草稿
- 校验与预览
- 发布动态快照
- 创建原生构建
- 查询构建状态和清单
- 激活、归档和回滚版本

接口不得让一个 `save` 同时承担保存草稿、动态发布和写代码包三种行为。

## 15. 校验、错误处理与安全

### 15.1 发布错误

以下问题阻止发布或构建：

- PageDocument 结构或版本不合法
- 组件不存在或组件版本不可迁移
- 节点 ID 重复、循环结构、深度或数量超限
- 属性、样式、数据源、动作或插槽不符合注册合同
- 动态页面使用仅支持编译的组件
- 动态快照要求高于当前目标运行时版本
- 动作越权、外链域名不允许或参数引用无效
- 编译模板占位符缺失或重复
- 生成文件语法、路径或包体积检查失败

### 15.2 发布警告

以下问题默认警告，管理员确认后可以继续：

- 图片尺寸或体积偏大
- 页面节点接近限制
- 活动画布过长
- 同屏请求的数据源过多
- 新构建比上一版本体积明显增加
- 组件使用了即将废弃的版本

### 15.3 信任边界

- 后端是页面合同和发布权限的最终校验者，不能只信任后台前端。
- 数据源和动作仍执行原业务鉴权、区域范围和参数校验。
- 动态配置不能控制支付金额、订单状态、用户身份或服务端权限。
- 素材上传继续执行类型、大小、路径和域名检查。
- 所有发布、回滚、应用到源码和构建操作写审计日志。

## 16. 组件首期范围

首期目标约 30 个组件，按实际复用价值交付，不为凑数量创建空壳组件。

### 16.1 布局组件

- 页面、容器、行、列、网格、卡片、横向滚动区、吸顶区、固定底栏、间隔

### 16.2 基础与展示组件

- 文本、富文本、图片、图标、按钮、分割线、标签
- 轮播、公告、模块标题、宫格、倒计时、折叠面板

### 16.3 表单组件

- 输入框、选择器、开关、单选、多选、图片上传、提交按钮

### 16.4 首批业务组件

- 信息流、推荐商家、用户卡片、消息入口、订单入口、优惠券、活动报名

具体数量可以因复用现有业务组件而调整，但组件注册、容器嵌套、编译和动态合同必须先于批量扩充组件库。

## 17. 迁移阶段

### 阶段 1：合同与注册内核

- 建立 PageDocument v2 类型、规范化、校验和 v1 迁移器。
- 建立组件注册中心以及文本、图片、按钮、容器四个参考组件。
- 建立后台属性面板从 schema 自动生成的最小闭环。

通过条件：四个组件能嵌套、保存、重新读取，并在后台预览中保持一致；未知组件不会丢数据。

### 阶段 2：新活动页动态闭环

- 建立新动态页面壳、运行时能力清单和不可变发布快照。
- 迁移常用 TMagic 文本、图片、按钮内容；复杂旧 DSL 继续只读和回退。
- 完成缓存、版本兼容和安全降级。

通过条件：后台创建活动页后，小程序不重新打包即可展示；断网、坏配置和不兼容组件均回退到旧版本。

### 阶段 3：首页运营插槽

- 在首页稳定宿主中接入新 `dynamic-slot`。
- 迁移轮播、宫格、公告、专题和弹窗。
- 校验运营内容不会覆盖或阻塞核心信息流。

通过条件：草稿不影响线上，发布只更新目标校区运营位，回滚恢复上一版本。

### 阶段 4：原生编译器试点

- 建立固定模板、组件片段编译、构建哈希、隔离工作区和构建清单。
- 先编译一个独立测试页面，不直接替换首页。
- 接入语法、快照、包体积和微信开发者工具检查。

通过条件：相同输入生成字节稳定的结果；无变化跳过构建；失败不修改现有源码或已完成构建。

### 阶段 5：核心页面迁移

- 先迁移首页结构，再迁移消息页和个人中心。
- 业务状态机和接口逻辑留在稳定宿主，页面结构改由生成片段承载。
- 每页完成自动化与真机验收后，才停用对应旧编辑入口。

通过条件：核心业务回归通过，旧版本可恢复，编辑器预览与真机结构一致。

### 阶段 6：收拢旧编辑器

- 把多个入口收敛到统一 UI Studio。
- 保留 v1 只读、导入和回滚窗口。
- 删除确认无引用的重复 schema、预览复刻和旧保存链路。

通过条件：所有生产页面已有 v2 版本或明确保留策略，旧接口没有活跃调用后才能删除。

## 18. 测试与验证

所有行为改动遵循测试先行。

### 18.1 合同测试

- PageDocument v2 正常、边界和非法结构。
- v1 到 v2 迁移确定性、幂等性和未知组件保留。
- 组件 props、slots、targets、dataSources 和 actions 合同。
- 规范化和构建哈希稳定性。

### 18.2 编译器测试

- 四类页面模板占位符完整性。
- 节点树递归编译和目标转义。
- 使用组件依赖与 `usingComponents` 生成。
- 相同输入字节稳定，内容未变时命中缓存。
- 组件或模板版本变化只重编译受影响页面。
- 临时构建失败不提升、不污染原源码。
- 生成 WXML/WXSS/JS/JSON 快照与语法检查。

### 18.3 动态运行时测试

- 只加载已发布文档，不读取草稿。
- 新远程版本、`304`/未变化、弱网、超时、损坏缓存和无缓存。
- 未知可选组件降级，未知必需组件保留上一版本。
- 数据源超时、空数据和服务端拒绝。
- 动作白名单、参数解析和审核模式限制。
- 全局模板与校区覆盖合并。

### 18.4 编辑器测试

- 拖拽、嵌套、跨容器移动、复制、删除、撤销和重做。
- schema 驱动属性面板，非法值不能进入可发布文档。
- 草稿自动保存不触发发布或构建。
- 发布差异和错误定位到具体节点、字段。
- 模拟数据的加载、空态和失败态。

### 18.5 集成与真实环境

- 后端聚焦单测、接口测试、Prisma 三 schema 一致性和生产构建。
- 管理后台类型检查与生产构建。
- 小程序纯函数、生命周期和页面合同测试。
- 微信开发者工具检查页面启动、数据加载、点击动作、动态回退和包体积。
- 真机检查安全区、不同屏宽、弱网、缓存、导航和业务主流程。

测试、构建、开发者工具和真机是四层独立证据，不能互相替代。

## 19. 验收标准

- 新增一个普通组件只需提供注册合同和目标适配器，不修改编辑器核心或巨型类型分支。
- 页面支持可校验的容器嵌套、Flex/Grid 流式布局和活动页绝对画布。
- 同一 PageDocument 能根据组件能力输出原生编译页面或动态页面。
- 核心业务逻辑不由 PageDocument 控制，支付、订单、登录和消息流程保持服务端及宿主代码约束。
- 保存草稿不发布、不生成代码包、不写小程序源码。
- 动态发布失败不替换线上快照；客户端失败不清除最近一次有效缓存。
- 原生构建失败不修改原源码或上一份可用构建。
- 构建产物具有版本、哈希、组件清单、文件清单、体积和验证报告。
- 活动页和首页运营位完成微信开发者工具验证。
- 首个核心编译试点完成自动化、开发者工具和真机验证后，才允许迁移首页。
- 旧页面在迁移期间正常工作，且有可执行的 v1 回退路径。

## 20. 实施约束

- 当前后端/后台和小程序工作区均存在用户未提交改动；实施必须按阶段隔离范围，不能覆盖校园地图等无关修改。
- 小程序目录是编译后的微信运行树，不能假设可以直接安装 UniApp/Vue 组件依赖。
- 新依赖必须证明现有平台、标准库或已安装依赖无法满足需求。第一期模板填充不增加 Handlebars/EJS。
- 数据库变更必须使用 additive migration，并同步 `schema.prisma`、`schema.postgresql.prisma` 和 `schema.mysql.prisma`。
- 每个阶段单独设计可回退边界和验收证据，不以“大平台最终会完成”为理由一次性修改所有页面。
- 未经明确授权，不执行服务器部署、生产数据库迁移、微信代码上传或线上动态发布。

## 21. 下一步

规格确认后，编写分阶段实施计划。第一份实施计划只覆盖“阶段 1：合同与注册内核”，不同时实现完整组件库、动态运行时和核心页面编译器。

阶段 1 通过后，再为阶段 2 编写独立计划。这样每个阶段都有可运行结果、测试证据和停止点，避免在脏工作区进行不可控的大爆炸式重写。
