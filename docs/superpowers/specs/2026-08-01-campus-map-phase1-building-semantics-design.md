# 一期校园地图单栋建筑语义化设计

日期：2026-08-01

## 1. 背景

当前一期校园 CAD 已完成基础精简，但导入后的用户体验仍接近工程线稿：建筑用途不清晰、楼栋名称不足、不同功能缺少视觉区分。学校提供的两张现场导览资料补充了正式编号、正式名称、已建/在建状态和总体空间关系。

本设计只处理当前第一期已建项目。宣传鸟瞰图中的后续在建项目保留为后台参考，不进入用户搜索、导航或发布地图。

## 2. 信息来源与优先级

1. CAD/GeoJSON：唯一的几何、坐标、道路、水体和建筑轮廓来源。
2. 现场《校园总导览图》编号表：正式编号、正式名称和已建/在建状态来源。
3. 宣传鸟瞰图：只用于核对大致空间关系、地标和视觉层级，不用于描绘精确坐标或建筑边界。

如果三类资料冲突，以 CAD 的实际几何和现场编号表的正式元数据为准。任何无法可靠匹配的项目必须进入人工确认，不能通过猜测发布。

## 3. 目标

- 一期已建项目细化到单栋楼或单个设施。
- 每个项目具有官方编号、正式名称、建设状态、所属期次、语义类型、搜索与导航权限。
- 用户能从颜色、名称和图标看懂宿舍、教学、餐饮、行政、运动、停车和校门等功能。
- 不把二、三、四期或其他在建项目误认为一期已开放设施。
- 保持小程序地图轻量流畅，不引入重型 3D 渲染。

## 4. 非目标

- 不以宣传鸟瞰图替代真实地图底图。
- 不凭建筑名称猜测未明确的用途。
- 不在本轮发布在建建筑、未来道路或未来服务点。
- 不自动覆盖当前区域草稿或已发布地图。
- 不新增独立业务数据库表；一期先沿用校园地图草稿/发布 JSON 和 GeoJSON 属性。

## 6. 数据模型

每个单栋建筑或设施至少包含：

```json
{
  "officialNumber": 3,
  "officialName": "天枢楼",
  "engineeringAlias": "",
  "phase": "phase1",
  "constructionStatus": "built",
  "semanticType": "building",
  "searchable": true,
  "navigable": true,
  "geometryStatus": "verified_polygon",
  "sourceConfidence": "official_signage_and_cad"
}
```

字段规则：

- `officialNumber` 与 `officialName` 来自现场编号表。
- `engineeringAlias` 保存“1号院、2A期”等工程名称，只在后台显示。
- `phase` 一期使用 `phase1`，后续项目使用 `future`，不擅自细分二、三、四期。
- `constructionStatus` 只允许 `built` 或 `under_construction`。
- `geometryStatus` 只允许 `verified_polygon`、`verified_point`、`point_only`、`unmatched`。
- `sourceConfidence` 记录匹配依据，避免后续把推测当成事实。

## 7. 图层与发布边界

地图数据分为三个相互隔离的集合：

1. `phase1_active`：一期已建且几何已核验的用户可见项目。
2. `phase1_review`：一期已建但轮廓或位置仍需确认的后台待处理项目。
3. `future_reference`：在建和后续项目，仅供后台参考。

发布时只读取 `phase1_active`。`phase1_review` 和 `future_reference` 即使存在于草稿，也不得被活动地图接口返回。

## 8. 几何匹配规则

- CAD 是唯一的轮廓来源；宣传图不能被描成正式建筑面。
- 建筑名称先通过空间位置和显著地标与 CAD 轮廓匹配，再由运营人员确认。
- 闭合建筑轮廓进入 `verified_polygon`。
- 只有可靠中心位置但缺少闭合轮廓时，使用 `point_only`，用户端只显示点位，不伪造建筑面。
- 无法确认位置时标记为 `unmatched`，只进入待人工确认清单。
- 入口和停车场可以使用点位或区域，不强制套用建筑面模型。

## 9. 后台体验

后台 CAD 清理工作台增加：

- 正式编号、正式名称、工程别名。
- 所属期次、建设状态、语义类型。
- 搜索开关、导航开关。
- 几何核验状态和来源可信度。
- “一期已建”“待确认”“未来参考”快速筛选。

应用导入结果前展示统计：一期活动对象数、待确认数、未来参考数、缺失轮廓数和重复编号数。存在重复官方编号、在建项目可搜索/可导航、或 `unmatched` 项目进入活动层时，禁止发布。

## 10. 用户端视觉与交互

### 10.1 视觉层级

- 总览：展示建筑组团、主要道路、水体、绿化和重要设施。
- 中等缩放：显示官方编号和正式名称。
- 近距离：显示建筑用途、入口和导航操作。

### 10.2 颜色

- 教学：青绿色。
- 宿舍：紫色。
- 餐饮：橙色。
- 行政：灰蓝色。
- 运动：绿色。
- 图书馆：蓝色。
- 校门：红色。
- 停车：深灰色。
- 用途未确认的校园建筑：中性蓝灰色。

颜色不能作为唯一信息。每个可交互对象同时显示名称、编号或图标，保证低视力和色觉差异用户仍能理解。

### 10.3 详情与导航

点击项目后显示官方编号、正式名称、用途、开放状态和导航按钮。只有 `built && searchable` 的项目进入搜索；只有 `built && navigable` 且坐标已校准的项目显示导航按钮。

## 11. 数据流

1. 清理工具读取一期 CAD 派生 GeoJSON。
2. 官方项目清单为特征补充正式元数据。
3. 自动匹配生成候选结果和待人工确认报告。
4. 运营人员在后台核验轮廓、编号、名称和状态。
5. 保存草稿，执行校准和发布检查。
6. 发布只输出 `phase1_active`。
7. 小程序刷新后加载活动地图，执行搜索、详情和导航。

## 12. 异常处理

- 重复官方编号：导入失败并列出冲突对象。
- 名称为空：不进入活动层。
- 一期项目缺少可靠几何：进入 `phase1_review`。
- 在建项目开启搜索或导航：发布检查失败。
- 宣传图位置与 CAD 不一致：以 CAD 为准并要求人工确认。
- GeoJSON 中文字段缺失：构建测试失败，禁止生成导入包。
- 发布后小程序未刷新：保留版本历史并允许回滚，不用重复导入覆盖。

## 13. 验收标准

### 数据验收

- 15 个已建编号全部存在且不重复：1–13、16、17。
- 22 个在建编号全部在 `future_reference`：14、15、18–37。
- 用户活动层中不存在 `under_construction` 项目。
- 每个活动建筑具有中文正式名称、官方编号和可靠几何状态。
- 3–13、16、17 在用途未确认时均保持 `building`，不自动误分类。

### 后台验收

- 可以按活动、待确认和未来参考筛选。
- 可以编辑单栋楼的编号、名称、类型和状态。
- 发布检查能拦截重复编号、在建项目暴露和未匹配几何。

### 用户端验收

- 总览能分辨建筑、道路、水体和绿化。
- 放大后能看到单栋楼编号和正式名称。
- 搜索只返回一期已建且可搜索的项目。
- 导航只对一期已建、可导航并完成校准的项目开放。
- 不依赖颜色也能通过文字或图标识别类型。

### 真实链路验收

- 后台导入一期数据并完成匹配。
- 保存草稿并通过校准检查。
- 发布新版本。
- 微信开发者工具或真机刷新。
- 搜索指定楼栋、打开详情并发起导航。
- 验证在建项目不出现在搜索结果和活动地图中。

## 14. 交付边界

实现阶段先生成新的“一期语义化后台导入版”文件和匹配报告，再调整后台与用户端。未经人工核验和真实链路验收，不覆盖已发布地图，不宣称生产发布完成。
