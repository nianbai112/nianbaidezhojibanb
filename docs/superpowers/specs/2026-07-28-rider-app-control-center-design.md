# 骑手 App 控制中心与首期可运行闭环设计

**日期：** 2026-07-28  
**状态：** 已确认方案 A，待书面规格复核  
**涉及工程：** `骑手端app`、`后端后台本地测试版/backend`、`后端后台本地测试版/admin`

## 1. 目标

首期交付一个真实可用的“骑手 App 控制中心”，并修复独立骑手 App 当前无法正常启动、无法读取正确 API 配置的问题。

控制中心必须能够安全地管理骑手 App 的版本、维护状态、公告、下载入口、定位上传频率和核心功能开关。所有保存操作必须有权限校验、服务端输入校验和管理员操作记录。

首期完成后，骑手 App 应当能够：

1. 正常启动，不再白屏。
2. 从固定的 HTTPS API 地址读取公开运行配置。
3. 在维护、版本过低和功能关闭时给出明确反馈。
4. 在配置接口暂时不可用时使用安全默认值继续进入登录页，而不是白屏。

## 2. 分阶段边界

本项目拆成三个可独立验证的阶段，避免同时改动全部履约链路后无法定位问题。

### 阶段一：App 控制中心与启动闭环

- 后台新增“系统管理 → 骑手 App 控制中心”。
- 后端新增类型化的管理员配置接口和公开配置接口。
- 骑手 App 修复启动错误、统一 HTTPS API 根地址、增加请求超时和启动配置加载。
- App 支持维护拦截、版本提醒/强制更新、公告和功能开关。

### 阶段二：身份与统一履约

- 打通微信登录、会话续期和 401 退出。
- 服务端强制校验审核通过、正式骑手、已绑定区域三项资格。
- 统一跑腿单与外卖单的订单池、详情和状态机。
- 修复新订单 WebSocket/系统通知事件契约。

### 阶段三：生产级配送能力

- 前台/后台持续定位、弱网缓存与轨迹补传。
- 导航、到店、取餐、送达证明、异常、转单和退单。
- 骑手收入明细、结算记录、提现状态和申诉入口。
- 用户、商家、骑手、运营四角色真实订单验收。

本规格的实施计划只覆盖阶段一。阶段二和阶段三各自形成独立规格与验收记录。

## 3. 方案选择

采用方案 A：复用现有 `Config` 和 `AdminOperationLog`，不新增配置数据表。

未采用方案：

- 独立 `RiderAppConfig` 数据表：会增加 Prisma 三套 schema、迁移和重复审计代码，首期没有查询或关联能力需要单独建模。
- 环境变量控制：无法在后台安全热更新，也缺少管理员修改记录。

## 4. 后端设计

### 4.1 配置存储

使用现有 `Config` 表中的单条记录：

- `key`: `rider_app_control`
- `group`: `rider_app`
- `value`: JSON 配置对象
- `createdBy`、`updatedBy`: 当前管理员账号 ID

配置对象固定为：

```ts
type RiderAppControlConfig = {
  enabled: boolean
  maintenance: {
    enabled: boolean
    title: string
    message: string
  }
  version: {
    latest: string
    minimum: string
    forceUpdate: boolean
    releaseNotes: string
    iosDownloadUrl: string
    androidDownloadUrl: string
  }
  notice: {
    enabled: boolean
    title: string
    content: string
  }
  runtime: {
    wsPath: string
    locationIntervalSeconds: number
  }
  features: {
    orderPool: boolean
    chat: boolean
    income: boolean
    incentives: boolean
  }
}
```

服务端补全缺失字段并拒绝无效值。版本号使用 `数字.数字.数字`；定位间隔限定为 15 至 300 秒；下载地址只允许空字符串或 HTTPS；`wsPath` 只允许以 `/` 开头的相对路径，禁止配置任意主机。

### 4.2 接口

管理员接口：

- `GET /admin/rider-app/config`：读取完整配置。
- `PUT /admin/rider-app/config`：校验并保存完整配置。

公开接口：

- `GET /rider-app/config`：无需登录，只返回 App 启动需要的安全字段。

生产环境全局 `/api` 前缀保持不变，因此外部地址分别为 `/api/admin/rider-app/config` 和 `/api/rider-app/config`。

### 4.3 权限与审计

- 新增权限码 `rider-app:config`。
- 只有拥有该权限的管理员可以查看和修改完整配置。
- 超级管理员通过现有全量权限逻辑自动获得该权限。
- 保存通过现有配置服务写入，并记录修改前后值、管理员 ID、IP 和时间。
- 公开接口不返回管理员信息、内部配置键或任何凭据。

## 5. 管理后台设计

新增路由 `/system/rider-app-control`，菜单名称“骑手 App 控制中心”，放在“系统管理”分组中。

页面分为四个卡片：

1. **运行状态**：App 总开关、维护开关、维护标题和说明。
2. **版本发布**：最新版本、最低版本、强制更新、更新说明、iOS/Android 下载地址。
3. **运行参数**：WebSocket 相对路径、定位上传间隔。
4. **功能开关与公告**：订单大厅、聊天、收入、奖励开关，以及公告内容。

页面只提供“保存配置”一个主操作。保存前在前端做基础校验，最终以服务端校验为准。维护模式、App 总开关、强制更新从关闭改为开启时显示二次确认。

骑手审核、订单、调度、申诉和结算继续使用现有菜单，不在控制中心重复实现。

## 6. 骑手 App 设计

### 6.1 固定启动地址

生产 API 根地址固定为 `https://yuntingzhe.cn/api`。开发调试覆盖值只在开发构建中可用，正式包不显示隐藏改址入口。

后台不允许远程修改 API 主机，因为 App 必须先连接 API 才能读取配置；远程修改会产生自锁和劫持风险。

### 6.2 启动流程

1. App 启动并读取本地版本号。
2. 以 10 秒超时请求 `/rider-app/config`。
3. 请求失败时使用安全默认配置并显示非阻断网络提示。
4. App 总开关关闭或维护开启时进入维护页。
5. 当前版本低于最低版本时进入不可跳过的更新页。
6. 当前版本低于最新版本但不低于最低版本时显示可关闭的更新提醒。
7. 配置允许后进入原有会话恢复或登录流程。

版本比较只比较三个数字段，不引入第三方依赖。

### 6.3 功能开关

功能关闭时同时执行两层处理：

- App 隐藏或禁用对应入口并显示“该功能暂未开放”。
- 阶段二为敏感业务接口补充后端开关校验，防止绕过界面直接请求。

首期只对尚未打通的页面做可见性控制，不把远程开关误称为服务端授权边界。

## 7. 错误处理

- 配置读取失败：不白屏，使用默认配置并允许进入登录页。
- 配置格式损坏：服务端返回校验错误；App 对缺失字段使用默认值。
- 保存失败：后台保留表单内容并显示服务端错误，不显示保存成功。
- 强制更新但当前平台没有下载地址：显示维护式阻断页面和客服联系提示，避免循环跳转。
- WebSocket 路径无效：后台禁止保存。

## 8. 测试与验收

### 后端自动测试

- 默认配置和旧配置补全。
- 非法版本、HTTP 下载地址、越界定位间隔和绝对 WebSocket 地址被拒绝。
- 公开接口不返回内部字段。
- 无权限管理员不能读取或保存。
- 保存后写入 `Config` 并产生操作日志。

### 后台验证

- 类型检查通过。
- 路由与菜单受 `rider-app:config` 权限控制。
- 四组配置正确回填、校验和保存。
- 三个高风险开关启用时出现确认提示。

### App 自动检查与运行验收

- 版本比较和配置规范化有独立测试。
- 配置请求失败、维护、可选更新和强制更新四种分支均可复现。
- HBuilderX/iOS 模拟器启动不再白屏。
- 后台修改公告和维护状态后，App 重新启动能读取新配置。

### 完成边界

本地测试与模拟器通过只证明阶段一完成，不代表真实微信登录、真机后台定位、生产部署或完整订单履约已经完成。

## 9. 非目标

阶段一不实现以下内容：

- 任意服务器地址远程下发。
- 热更新代码或绕过应用商店更新。
- 骑手审核、订单调度、结算页面的重复版本。
- 阶段二和阶段三列出的完整履约功能。
- 生产部署与应用商店发布。

## 10. 交付顺序

1. 后端配置类型、默认值、校验、权限、公开/管理接口和测试。
2. 后台菜单、路由、表单和危险操作确认。
3. 骑手 App 启动修复、请求层、配置加载、维护/更新状态和功能开关。
4. 后端全量测试、后台类型检查、App 自动检查和模拟器取证。
