## 〇、先回答你的三个问题

### 1. 各目录是什么？微信小程序在哪？

| 目录 | 角色 |
|---|---|
| `backend/` | NestJS + Prisma 后端，65 个业务模块，是整个平台的核心 |
| `admin/` | Vue3 + Element Plus **管理后台前端**（桌面端），就是你说的"桌面的前端文件" |
| `site/` | 一个独立的官网/落地页（Vue，只有 App.vue + 配置），和外卖业务无关 |
| `minitest/` | 4 个零散的验证测试脚本 |
| `backend/src/modules/miniapp/` | 只是给小程序提供配置的**后端接口**，不是小程序本身 |

**⚠️ 这个文件夹里没有微信小程序源码，也没有骑手端 App 源码。**
用户端小程序（uni-app/Taro/原生小程序工程）应该在你电脑的其他位置。骑手端目前的形态是：**小程序里复用跑腿模块的"接单大厅"页面**（后端 errand 模块里有完整的骑手接口），并没有独立的骑手 App。

### 2. 外卖板块为什么"一直卡壳"？——一句话诊断

**正向流程（浏览→购物车→下单→接单→出餐→骑手配送→送达→评价）其实已经打通，完成度约 85%；卡壳的根源是：所有"异常分支"和"资金后半段"都是空的。** 商家不能拒单、用户付款后不能取消、退款接口完全不存在、结算/佣金/骑手工资从不落账。跑一天订单，系统不知道该给商家、骑手、平台各分多少钱。这就是"看起来能跑、但永远不敢上线"的原因。

### 3. 跑腿 vs 外卖的关系

外卖单（Order 表）**不会**转成跑腿单（ErrandOrder 表），而是复用了跑腿的骑手身份体系（RegionRider）和骑手接单接口：骑手在接单大厅看到混合列表，接单接口先查跑腿表、查不到就当外卖单处理（`errand.service.ts:2027` 一行 if 分流）。另外 `delivery/` 模块是**历史遗留空壳**（旧的第三套配送实现，订单池永远为空、骑手永远 403），但它恰好是唯一往 Redis 写骑手位置的代码——导致外卖"就近推送骑手"功能**永久失效**。

## 一、外卖全链路现状图

```
浏览店铺 ✅ → 购物车 ✅ → 下单 ✅(优惠券/会员/库存原子扣减/距离/营业时间校验都有)
   → 支付 ⚠️(payment模块负责，0元单直通) → 商家接单 ✅ → 商家拒单 ❌不存在
   → 超时未接单 ⚠️只提醒不处理 → 出餐完成 ✅ → 推送骑手 ⚠️就近排序失效
   → 骑手抢单 ✅ → 取餐 ✅ → 送达 ✅ → 确认收货 ✅(24h自动)
   → 评价 ⚠️(一单只能评一个商品、店铺评分永远5.0) → 退款/售后 ❌完全不存在
   → 商家结算 ❌从不生成 → 平台佣金 ❌只在前端展示 → 骑手工资 ❌零落账
```

## 三、产品视角：离"真正的外卖板块"还差什么

**订单状态机需要重构**：现在 PAID 一个状态靠 `merchantAcceptTime/readyTime/pickupTime` 三个时间戳拼出"待接单/备餐中/待取餐/配送中"四种语义，判断逻辑散落 5+ 处。应引入显式状态：`MERCHANT_ACCEPTED`（商家已接单）、`READY`（出餐完成）、`PICKED_UP`（骑手已取餐）、以及 `MERCHANT_REJECTED`。

**缺失的数据模型**（表都不存在）：骑手排班、配送费阶梯规则（现在外卖配送费只是商家单一定值，不支持距离/时段/天气加价）、结构化营业时间（现在是裸字符串）、库存流水、每日备货/沽清、派单记录、分账快照字段（riderIncome/platformCommission/merchantIncome 应在成单时冻结）、商家资质及有效期。

**建好了表但一行业务代码都没有**：`Promotion` 满减、`FreightTemplate` 运费模板、`OrderAppeal`（后端零读写但前端页面已经在调 PATCH 接口）、`RiderSettlement` 全家桶、`RegionMerchantSettings` 全部字段（佣金率、商品审核开关等只存不用）。

**派单体系真相**：所谓"派单算法"其实是接单可行性评分器，距离用中文关键词（"东区""食堂"）字符串匹配而非经纬度；无自动派单、无超时改派、无二次广播（跑腿单只在创建时广播一次）。

**骑手端产品建议**：先不要做独立 App。合理路径是——第一步把小程序内的骑手角色页面做扎实（接单大厅修分页、加定位上报、加收入明细页）；第二步等单量起来再考虑独立骑手小程序；App 是最后一步。后端需要先补齐：骑手收入落账、提现、位置轨迹、多单叠单。

### 诊断修正（连接完整代码库后核实）
初版报告基于部分模块，以下结论需要修正：
1. **"expirePendingPayment 无人调用" 不成立**——`scheduler/payment-expiry.service.ts` 每分钟对账并调用它，恶意锁库存风险实际有兜底。
2. **"商家无法拒单" 部分不成立**——`POST /wxpay/merchant-refund` 就是商家拒单实现（接单前全额退款），小程序商家端"拒单退款"按钮已接入。缺的是接单后的处置和超时自动处置。

4. **"用户退款完全缺失" 部分不成立**——接单前自助退款 `POST /wxpay/user-order-refund` 已存在且小程序已接入；后台退款审核（admin/refunds audit → executeRefund/rejectRefundById）完整。**真正的洞是：商家接单之后，用户从此没有任何退款入口**。
5. 微信小程序源码在"前端文件"文件夹（原生小程序），骑手端 App 在"骑手端app"文件夹（UniApp，5 个页面的官方骑手端雏形）。

## 七、2026-07-26 第二批改动记录：安全线（已落地）

全部完成并通过验证（后端全仓 tsc 0 错误；errand-closure 集成测试 9/9、shop.service 单测 72/72 通过）。

**B1 骑手隐私泄露（最严重）**——`errand.service.getRegionRiders` 以前用 `...rider` 展开整条记录返回，任意登录用户可拉取全平台在线骑手的身份证号+支付宝账号+手机号。改为：必须是认证骑手才能调用，只返回**调用者所属区域**的骑手，且只输出 `publicRiderProfile` 公开字段（无身份证/支付宝/手机号）。控制器补传 `userId`。（小程序 Grab.js 只用它选转单目标，字段够用，不受影响。）

**B2 order-center 越权**——`getRefunds`/`getPaymentByNo` 以前不校验数据范围，区域管理员可读全平台退款和任意支付单。改为按 `AdminDataScope` 限定：区域管理员的普通退款按商户 regionId 过滤、商城退款（平台级）对其隐藏；查支付单会校验对应订单是否属于其区域，否则 403。控制器补传 `operatorId`。

**B3 跑腿取消/接单竞态**——`cancelOrderUnlocked` 以前用无条件 `update`，且取消锁 key 与接单锁 key 不同，导致"用户点取消"与"骑手接单"并发时能把在途订单改成 cancelled 并全额退款、骑手白跑。改为带 `status IN [pending_pay,pending_accept]` + `riderId: null` 守卫的条件 `updateMany`，`count !== 1` 即拒绝——无论锁是否对齐，竞态都不可能得逞。

**B4 骑手实名信息防篡改**——① `updateRiderInfo`：审核通过的骑手若尝试改姓名/身份证（与现值不同）直接拒绝，提示联系平台重新认证；② `applyRider`：以前 upsert 的 update 分支会把 approved 骑手打回 pending+offline，绕过"有进行中订单不能下线"的校验，现在已认证且有在途订单时禁止重新提交申请。

**B5 下线遗留 delivery 模块 + 修复就近推送**——`delivery` 是历史空壳（订单池恒空、`orderPool` 越权泄露地址电话），但它是唯一往 Redis `rider:location` 写数据的地方，而外卖"就近推送骑手"依赖这个 key 排序。处理：先把 Redis 位置写入迁移到 `ErrandService.updateLocation`（骑手定位上报时同时写 DB 和 Redis），再从 `app.module.ts` 注销 `DeliveryModule`（越权接口随之下线）。副作用是外卖就近派单排序恢复生效。

### 关于"Node.js 能否扛高并发"的结论
能。外卖是 IO 密集场景，Node 事件循环天生适配；瓶颈不在 Node 而在：数据库慢查询/缺索引、串行 IO 循环（如 `notifyAvailableRiders` 持锁期间给全区骑手逐个查库发通知）、单进程部署、事务内做外部调用。解决方向：优化慢查询加索引、把串行循环改并发且移出锁、PM2 cluster/Docker 多副本跑满多核、外部调用移出事务。不需要换语言或重构架构。
