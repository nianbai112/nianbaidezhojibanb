## Go 架构建议

A（当前推荐）：继续使用现有 NestJS 后端，先改增量绘图、静态资源压缩、公开地图版本/缓存。CAD 已退出运行链路，不再需要为它迁移独立 Worker。

B（后续可选）：同机增加独立 Go 地图读取服务，通过 Nginx 按 URL 分流；首先只消费已发布快照。采集、审核、保存、发布继续由原后端唯一写入。需要版本指针、撤回/停用传播、接口兼容、鉴权、超时、资源上限、监控和回切验证后再灰度启用。

不建议一次性将整个校园地图业务重写为 Go，也不建议两个后端同时写同一份路线审核状态。同机双语言不等于两套硬件，仍共享 CPU、内存、带宽与数据库；语言变化无法直接修复浏览器或手机绘图开销。

技术可行性参考：[NGINX 反向代理](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)、[Go 性能诊断工具](https://go.dev/doc/diagnostics)。是否更快须比较实际工作负载，不能凭语言承诺倍数。
