# 跑腿收入自动转入微信零钱：实现与发布说明

日期：2026-09-17。服务端、管理后台及增量数据库迁移已发布，自动转账保持关闭，未调用真实付款接口。小程序源码已同步服务器，微信版本和骑手 App 新包尚未发布，仍需真机授权及小额联调。详见 [服务器发布记录](./2026-09-17-rider-wechat-payout-deployment.md)。

## 用户使用流程

1. 骑手使用绑定的微信打开小程序，确保与骑手端手机号登录对应同一个平台用户。
2. 进入「我的钱包 → 跑腿收入自动到账」，完成一次微信收款授权。服务端向微信核实授权生效后才允许自动付款。
3. 骑手可以在小程序或手机号登录的骑手 App 接跑腿单。
4. 用户确认收货、有效收货码核销或满足原有自动确认规则后，沿用已有平台抽成和结算逻辑。
5. 系统将该笔实际入账的净收入转入授权的微信零钱。原有退款负债先抵扣；用券订单不设固定等待期，防刷券、申诉、退款和风险校验继续生效。
6. 小程序收款页与骑手 App「收入与钱包」显示授权状态和最近到账记录。只有微信查单确认 SUCCESS 才显示「已到账微信零钱」。

骑手仅点击到达，不触发付款。有对应微信用户还不够，必须是同一平台用户且已完成授权。授权前的历史余额继续走原提现流程。

## 优惠券与骑手报酬（补充核验）

当前结算口径为：骑手应得金额 = 优惠前配送费 + 小费 − 平台抽成。优惠券和会员折扣由对应补贴方承担，不再次从骑手收入中扣除，也不在已含补贴的配送报酬之上重复加一遍券额。平台发券由平台承担；区域券等沿用补贴账本记录的承担方。

按用户确认的规则：抽成基数为优惠前总金额，即配送费原价＋小费；优惠券、会员折扣不减少抽成基数。合法全额抵扣订单正常生成可接单订单，也按原总金额抽成。费率、启用状态和固定手续费继续读取后台设置；总手续费最多为原总金额，不固定写死为 10%。

例如配送原价 10 元、无小费、无历史负债，抽成设置为优惠前总金额的 10%、固定费 0：

| 用券金额 | 用户实付 | 平台抽成 | 骑手应得 |
| --- | --- | --- | --- |
| 0 元 | 10 元 | 1 元 | 9 元 |
| 8 元 | 2 元 | 1 元 | 9 元 |
| 10 元 | 0 元 | 1 元 | 9 元 |

用券订单在用户确认收货或有效收货码核销时，防刷校验通过即结算并触发自动转账，不创建 48 小时冷静期。既有退款负债等仍按原规则抵扣；实际命中防刷、未结申诉或退款的订单继续拦截。实际到账以微信成功结果为准。

优惠券只是一笔优惠和补贴记录，不会给微信运营账户增加现金。发券方必须准备实际出款资金；商家转账从运营账户支出，需提前补足余额，详见[微信运营账户充值说明](https://pay.wechatpay.cn/doc/v3/merchant/4013747269)。资金不足会影响实际付款时间，不应改小骑手应得金额来消除缺口。

测试覆盖不用券、部分用券、全额抵扣、券面额超过订单原价、会员优惠叠加、小费、关闭抽成，以及确认收货同一事务内向自动出款模块传入完整净收入。10 元订单配置 10% 抽成时，无论用户实付 10 元、2 元或 0 元，均按 1 元抽成、9 元骑手净收入处理。重复确认不能再次出款。

采用 A 方案：小程序完成授权，后端统一结算，两端共用记录。B 方案是每单另行进入微信确认收款；本次未采用，因为不能满足完成订单后自动到账的需求。是否能使用免确认授权接口，以当前商户的实际权限和微信接口结果为准，开通「商家转账」的截图不能替代联调验证。

## 后台入口与配置

「系统设置 → 第三方配置 → 微信支付配置」增加以下字段：

| 配置 | 默认值 | 用途 |
| --- | --- | --- |
| 跑腿收入自动到账 | 关闭 | 开启后仅对已授权骑手的后续合格收入生效 |
| 商家转账场景 ID | 1005 | 佣金报酬，需与微信获批场景一致 |
| 自动转账单笔上限 | 200 元 | 对应提供的商户截图；整单超额保留在钱包，不拆单 |
| 每位骑手每日上限 | 2,000 元 | 上海时区，额度不足则延后 |
| 商户每日上限 | 50,000 元 | 只统计本系统自动转账，其他渠道也会消耗微信实际额度 |
| 骑手收款授权回调地址 | 空 | 真实公开 HTTPS API 地址，以 `/wxpay/rider-authorization-notify` 结尾 |

例如 API 对外根地址为 `https://api.example.com`，则填写 `https://api.example.com/wxpay/rider-authorization-notify`；如果反向代理对外使用 `/api`，须包含该前缀。推荐地址按钮生成的结果仍需按实际部署核对。本地 HTTP 地址不能用于微信通知。

商户号、商户私钥、证书序列号、APIv3 密钥沿用原支付配置；微信平台验签公钥或平台证书由后端管理，后台保存不会覆盖它们。密钥不下发客户端。

本版本单笔配置范围为 0.10～1,999.99 元，未实现更大金额所需的姓名加密流程。净收入不足 0.10 元时完整保留在钱包，不冻结、不发起无效付款，后续可随余额按原提现流程处理。[微信最低转账金额说明](https://pay.wechatpay.cn/doc/v3/merchant/4013778940)。提高后台数字不会提高微信商户获批额度。

## 付款与异常处理

- 结算收入、冻结出款金额、生成唯一付款指令在同一个数据库事务内完成。每个跑腿订单最多一条自动付款记录。
- 同一笔自动出款同步登记现有提现流水，冻结金额不可再次手动提现。原先的钱包总收入、总支出继续可对账。
- 微信请求、响应和授权通知验签；通知使用原始报文并进行 AES-GCM 解密。客户端弹窗成功不等同于授权完成。
- 付款单号和请求内容在调用微信前持久化。超时先查单；只有经过验签的「单号不存在」响应才允许沿用原单号重试，不新建替代付款单。
- 跨天重试重新检查当日额度，仍沿用原单号。未知结果超过 24 小时后停止自动重发，保留冻结并每小时核对；需人工介入时通过微信商户平台对账及审计处理，不直接释放或补发。
- 微信确认失败才退回平台钱包。尚未发出的款因关闭功能、撤销授权或结算条件变化取消时，也退回钱包；结果未明的款继续冻结。
- 后台「财务 → 提现」标注自动转账，并提供「核对到账」。此按钮只查询微信，不发起新的付款。自动记录禁止使用人工填写流水号的方式标记成功。
- 关闭平台开关后不再预留新出款，已发起的款继续查单。不要因此停止 worker，也不要删除原商户验签或查询所需配置。

即时发起不等同于承诺每一单秒到账；微信处理、账户余额、额度及风险限制会影响实际到账时间。

## 数据库与发布顺序

新增 `rider_wechat_authorizations`、`rider_wechat_payouts` 两张表；未修改历史订单或钱包金额。PostgreSQL 与 MySQL 均提供 `202609170001_rider_wechat_payout.sql` 增量迁移。两份 schema 已同步，迁移内容与 Prisma schema 差异一致。

在目标环境按现有发布流程操作，先保持自动转账关闭：

1. 备份数据库，核对目标环境的 `DB_PROVIDER` 和 `DATABASE_URL`。
2. 在 `backend` 目录生成对应数据库客户端：`npm run db:generate`。
3. 查看待执行迁移：`node scripts/migrate-release.cjs status`。该工具会创建迁移账本，不能当作完全只读探测。核对全部待执行项后，使用 `node scripts/migrate-release.cjs apply`，随后确认本次迁移为 APPLIED。
4. 按原发布流程构建并更新 API 服务和独立 worker。两者都要更新：API 在结算后唤起付款，worker 每 5 秒补偿处理。Redis 的续期锁协调多进程；首次发送和跨天重试还在数据库 Serializable 事务内复核并占用每日额度，防止租约失效时多个任务突破本系统限额。
5. 发布后台、小程序和骑手 App。骑手 App 只增加展示入口；自动结算由后端完成，小程序承担首次微信授权。
6. 核对商户权限、1005 场景、API 实际公网出口 IP 白名单、运营账户可用资金和回调可达性。截图中的 IP 不能代替部署后的实际出口核对。
7. 填写配置后开启功能，用一个测试骑手先完成授权，并用一笔小额真实订单验证后再推广。

旧版本已生成的纯优惠等待记录（`marketing_cooling_period` / `marketing_cooling_period_backfill`）由 worker 直接重新检查，不再等旧到期时间：已确认收货且风险校验通过的未结算订单采用当前后台费率、按原总金额计算后入账。实际风险或人工审核记录不自动放行；已存在有效结算明细的订单不重算、不重复入账。旧迁移文件保持原样，以免破坏线上迁移校验。

注意：`migrate-release.cjs apply` 会执行该版本所有待执行增量迁移，不只这一份。不要在已有数据库上使用 `install` 或 `db push --accept-data-loss` 代替增量发布。

## 上线验收

- 首次授权：小程序弹出正确商户的收款授权页，后台查单为 TAKING_EFFECT，刷新后两端均显示已开通。
- 手机号登录：在骑手 App 接单，到达后收入不提前转账；完成有效确认后，扣除后台配置抽成的实际净额自动发出。
- 核对同一笔订单的应付净额、平台钱包冻结/支出、微信商户流水和骑手零钱账单。重复确认收货不得再次付款。
- 撤销授权或关闭开关后，新的合格收入留在平台钱包。已有付款继续核对。
- 正常用券订单确认收货后不等待；超限、实际风控拦截、未结申诉等仍按上面的额度及风险规则处理。
- 网络超时测试使用模拟环境，不人为制造真实重复转账；未知结果不得手工补发。

## 本轮全面检查发现并修复的问题

1. **并发负债抵扣重复扣钱。** 旧实现中，两笔各应得 9 元的订单同时读取同一笔 4 元负债后，钱包只增加 10 元，但负债记录只回收 4 元；正确结果应为 14 元。已在独立数据库复现旧问题。自动入账和财务人工结算均增加原负债金额、已收回金额、状态校验，冲突时整个事务回滚，重试后只抵扣一次。
2. **当天首批订单并发创建结算单冲突。** 日结算单具有两个唯一键，原 upsert 会在两单同时首次入账时出现唯一键错误。改为允许唯一冲突跳过的空表头插入，再原子累计金额，两单均可正常入账。
3. **仅依赖 Redis 租约控制每日额度。** 进程长时间暂停或锁过期后，不同任务可以同时读到同一剩余额度。付款前数据库采用 Serializable 事务检查额度并登记发送时间；冲突的任务回滚，尚未获得额度不会调用微信付款接口。
4. **微信必填请求头遗漏。** 按[用户授权后转账官方接口](https://pay.wechatpay.cn/doc/v3/merchant/4014399371)补齐 `Wechatpay-Serial`，同时支持平台公钥 ID 和平台证书配置；它与商户自己的证书序列号分开使用。
5. **付款结果与内部账目一致性校验不足。** 结束出款前核对提现单的用户、金额、渠道和状态，以及唯一且金额相同的待处理钱包流水；缺失、重复或不符时整笔数据库事务回滚，保留冻结继续核对，不伪造到账。
6. **授权状态的异步乱序。** 延迟到达的待确认结果不能覆盖已经生效的授权，已关闭授权不能被旧响应恢复。付款前查授权也核对响应中的收款人、商户、AppID 和场景，发现不一致取消尚未发送的款。
7. **微信最低金额边界。** 不足 0.10 元的净收入保留在钱包，不发出必然不满足限额的请求；后台不能把限额配置成低于微信最低金额。
8. **金额计算与后台预览。** 抽成改用十进制四舍五入，修正 `1.45 × 10%` 被浮点计算成 `0.14` 的情况，正确手续费为 `0.15`。后台计算器按整数分计算并与后端校验一致，关闭抽成时预览也显示零抽成。
9. **MySQL 并发插入后的旧快照。** 在真实 MySQL 8.0 的默认 REPEATABLE READ 隔离下，Prisma `update` 的预读看不到另一事务刚创建的日结算单，导致 P2025。日结算单和钱包改为跳过重复插入，再使用 `updateMany` 原子累计并校验更新数量，最后读取本事务已更新的记录。测试以同步屏障固定复现旧快照；MySQL 与 PostgreSQL 均通过。

这次修改没有新增用券等待期，也没有放开自接单、关联账户、退款、申诉或实际风险拦截。10 元原价按 10% 抽成、无固定费和历史负债时，不用券、用 8 元券、用 10 元券均为骑手 9 元。

### 真实数据库审查脚本

新增 `backend/test/rider-payout.database.audit.cjs`。脚本拒绝非本机地址、非 PostgreSQL/MySQL 连接及名称不以 `rider_payout_audit_` 开头的数据库；不加载项目的业务数据库配置，不发起真实微信请求。它会写入测试账号、订单、账目和测试配置，必须使用新建的可丢弃数据库。

先用 `schema.postgresql.prisma` 为临时数据库建表，并将 Prisma PostgreSQL 客户端单独生成到临时目录，再在 `backend` 目录执行：

```sh
RIDER_AUDIT_DATABASE_URL='postgresql://本地用户@127.0.0.1:55439/rider_payout_audit_demo' \
RIDER_AUDIT_PRISMA_CLIENT='/临时目录/client' \
node test/rider-payout.database.audit.cjs
```

该脚本保留测试记录便于检查；结束后关闭并删除专用测试实例即可，不应对现有数据库运行清库命令。

## 微信官方接口依据

实现采用[收款用户授权接口](https://pay.wechatpay.cn/doc/v3/merchant/4015901167)、[小程序授权调起说明](https://pay.wechatpay.cn/doc/v3/merchant/4015930512)、[用户授权免确认转账](https://pay.wechatpay.cn/doc/v3/merchant/4014399371)、[转账查单](https://pay.wechatpay.cn/doc/v3/merchant/4024814206)和[授权结果通知](https://pay.wechatpay.cn/doc/v3/merchant/4014512908)。授权免确认转账的到账结果按查单核实，未把授权通知当作付款成功通知。
