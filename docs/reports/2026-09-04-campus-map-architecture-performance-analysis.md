# 校园地图架构与性能分析

检查时间：2026-09-04 15:01—15:04，中国标准时间。

范围：线上只读状态检查、少量串行 GET 请求、部署配置和源码检查。未修改生产配置、地图、数据库或程序；未执行压力测试。源码以校园路线独立工作树及本地学生端为依据，不等同于已验证线上所有前端包一致。

## 结论

可以拆分。推荐 A：先优化终端绘图，再将公开地图读取、静态资源与后台重任务分开。暂不推荐 B：立即重写为独立地图微服务/GIS 平台。

目前没有证据证明服务器正在资源耗尽，更不能依据后台操作卡顿断言大量学生使用一定导致服务器崩溃。已发现具体性能风险，但没有浏览器性能录制和真机帧率数据，不能把其中某一项认定为本次卡顿唯一根因。

## 1. 当前是什么架构

这是“模块化业务后端 + 按角色拆进程 + 客户端绘图”的架构，不是独立校园地图服务。

```text
后台管理员
  └─ Vue 地图工作台
       ├─ 画师图：OpenLayers，完整 SVG 底图 + 可编辑矢量图形
       └─ 真实地图：高德 JS 地图 + 地点/区域/路线覆盖物

学生小程序（本地代码）
  ├─ 内置画师 SVG + Canvas/界面标记
  ├─ 从服务器读取已发布地点与路网
  └─ 本机计算路线、定位更新和绘图

线上同一台服务器
  ├─ Nginx：官网、后台静态文件、接口反向代理
  ├─ API 进程：校园地图与其他业务模块
  │    └─ 当前 CAD 导入处理也从这里启动
  ├─ Worker 进程：已有后台任务，但尚未接管校园 CAD 导入
  ├─ Realtime 进程：实时消息连接
  ├─ MySQL：地图草稿、发布版本、地点、采集审核等业务数据
  └─ Redis：已有基础设施；地图公开读取链路未看到专用结果缓存
```

重要区别：拆为多个进程不等于拆成多台服务器。现在 CPU、内存、磁盘、网络仍共享；地图也仍在通用 API 内。

真实导航坐标和画师图展示坐标必须继续分别保存。任何性能重构都不应把二者合并，或通过简化展示线改坏真实导航拓扑。

## 3. 已确认的问题和边界

### 3.1 后台部分修改触发全量重建

画师图工作台深度监听地点、建筑、路线等数组，变化后执行 source.clear()，重新创建并添加所有图形；真实地图也有 clearAmapOverlays() 后重新创建覆盖物的路径。历史撤销快照包含完整地图 JSON 的复制和序列化。

这是数据增加时的明确开销点。不能由此声称每一次普通平移都会触发重建；需通过实际交互录制确认触发频率与耗时。

优先修法：按对象 ID 增量更新，变化只影响对应对象；草稿线和选中态独立处理；合并重复刷新；限制历史快照体积；复用样式。

### 3.2 后台完整 SVG 尚未压缩

线上 SVG 已有 30 天浏览器缓存，并不是完全没有静态缓存。但当前 URL 是固定文件名，同时标记 immutable；若覆盖同名文件，客户端存在沿用旧图的风险。

优先修法：内容哈希/版本化 URL + SVG 压缩；根据真实设备测量再选择多分辨率图片或切片底图。原始 SVG 保留供编辑和高质量导出。

当前 OpenLayers 用 ImageStatic 加载底图，不能把 SVG 的 1.45 万个元素误说成 Vue 同时挂载了 1.45 万个 DOM 对象。压缩下载也不减少 SVG 解析后的图形复杂度。

学生端本地代码使用内置底图，不可直接把后台未压缩下载定为学生端慢的原因。

### 3.3 公开读取仍走数据库

getActiveMap 读取已发布版本，再查询允许公开的地点和媒体，过滤撤回内容。这里没有看到地图专用缓存；线上接口也没有返回明确的 Cache-Control。接口已有 gzip 压缩。

学生端再次显示页面时会请求完整公开配置，再比较版本是否变化；不是只请求一个小版本号。

优先修法：轻量版本/状态接口 + 按版本的公开地图包缓存；发布、停用、撤回时明确失效。不得将鉴权接口无差别共享缓存，不能缓存草稿，更不能让撤回内容长期继续公开。

特别注意：版本号未变不等于开放状态未变。新设计要同时跟踪停用/撤回状态版本，保证必要的安全更新能生效。

### 3.4 CAD 重任务尚未真正隔离

生产编译代码确认使用 setImmediate 启动 processImportJob；解析处理仍由 API 中的服务执行，转换器部分通过子进程调用。setImmediate 只延后执行，不会自动变成独立 Worker。

已有 Worker 可作为迁移基础，但需要明确队列、限并发、超时、重试、幂等、状态和失败恢复。地图发布的校验/编译也是管理侧工作，未来数据变大后再评估异步预编译，不应把目前版本事务简单搬走破坏一致性。

### 3.5 学生拖图不是每帧向服务器要一张新图

本地小程序代码在终端执行 findCampusRoute 和重新规划；拖动缩放也在本机更新画布与界面。已有约 16ms 合并绘图、手势时减少标记处理等优化。

因此扩容服务器不能直接解决手机绘图卡顿。下一步应测量低端真机首屏、拖动帧耗时、内存、setData 开销及长时间导航表现。

## 4. A/B 方案

### A：保留业务系统，做轻量读写分离和任务隔离——当前推荐

```text
管理员采集/审核/编辑 → 原业务 API → 草稿与审核数据库
                                      ↓
                           受控发布/打包任务
                                      ↓
                     版本化公开地图包 + 静态底图
                                      ↓
                  Nginx / 对象存储 / CDN → 学生读取

轻量状态接口 → 当前版本、学校停用和内容撤回状态
独立 Worker → CAD 转换、解析、预生成等重工作
客户端 → 渲染、标记交互、基于已发布路网寻路
```

第一阶段可以继续用现有服务器，先改善绘图和压缩。CDN/对象存储及独立任务机器按实际流量逐步增加，不要求一次全部上。

收益：减少重复查库和重复下载，避免后台重任务争抢 API 执行资源，保留现有采集审核发布链路。前端绘图仍需单独优化。

仍共享主机时不具备整机故障隔离；仍共享数据库时也不具备数据库故障隔离。不能把逻辑拆分宣传为彻底隔离。

### B：独立地图服务/地图平台——现在不推荐立即实施

地图独立 API、计算进程与部署，必要时独立数据库/空间索引、瓦片生产与分发；再根据数据形态评估专业 GIS 工具。

适用条件：多校园显著增长，路网/图形数量和空间查询需求增加，或经过压测确认 A 仍不能满足峰值/隔离要求。

代价：认证和数据同步、部署与监控、版本一致性、回滚、故障恢复都要新增维护。仅把接口换个服务地址不会改善后台全量重绘，也不会减少手机 SVG 解码成本。

## 5. 建议实施顺序与验收

1. 先明确卡顿端、具体操作、目标设备和预计峰值；录制一次真实卡顿，建立基线。
2. 修后台增量绘图、合并刷新；开启 SVG 压缩并采用版本化资源 URL。
3. 将版本检查和大包读取分开；建立安全缓存与撤回失效机制。
4. 将 CAD 重处理迁入可控 Worker；保护 API 的时间和内存预算。
5. 在测试环境用接近生产的数据，按目标并发逐级压测，测 p95/p99 延迟、错误率、带宽、数据库和事件循环。
6. 根据实际测量决定是否追加 CDN、独立任务机器或方案 B；不凭用户总数直接购买配置。

必须保留的正确性验收：采集 → 审核 → 保存 → 发布 → 客户端更新；草稿不泄露；停用/撤回及时生效；真实路网连通性不变；画师展示线仍可调整。
