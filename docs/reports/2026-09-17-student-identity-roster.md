# 学生名册认证：最终实现与交付记录

本次最终规则以用户 2026-09-17 的明确纠正为准：**学生姓名和学号与本校花名册一致，自动认证成功；不一致则提交证明材料，进入人工审核。** 不要求激活码，不要求事先确认本人，不增加凭证发放流程。此前“名册＋个人凭证”的方案及早期测试记录已经被本实现替代。

实现已完成本地开发与隔离验证。未部署到正式服务器，未向正式数据库导入花名册，也未切换线上学校的认证方式。现有工作区包含其他任务的骑手提现改动，本次未提交或发布整个工作区。

## 最终行为

| 情况 | 处理结果 |
| --- | --- |
| 本校名册的姓名和文本学号完全匹配、在校、身份未被其他账号占用 | 直接通过，绑定账号，不上传学生证 |
| 学号不存在、姓名不一致、绑定冲突 | 提示补充学生证，提交后进入人工审核 |
| 人工审核发现填错 | 可更正姓名、学号后审核；能对应名册的绑定对应学生 |
| 学校认可但尚未进入花名册的学生 | 可人工通过，作为“名册外人工通过”单独统计 |
| 同一名册学生已被其他账号绑定 | 不允许人工审核直接抢占，先处理绑定争议 |
| 毕业、退学或人工撤销 | 撤销本校学生权限，保留平台账号及历史记录；已撤销账号再次申请须人工复核 |
| 原有已通过认证 | 保留，未对应新名册的单独显示，不按同名强行关联 |
| 其他学校未启用名册方式 | 继续人工材料审核 |

姓名、学号核对证明信息在花名册中，不证明操作者本人。按用户选定规则实现，未将此功能表述为能完全杜绝冒用。

学号按文本处理：保留前导零、字母大小写、连字符和不同长度；没有固定 9 位、14 位或纯数字限制。输入去掉首尾空白，最长 191 个字符，拒绝控制字符。学校范围和学号摘要构成唯一键，避免 MySQL 默认大小写不敏感排序规则合并不同学号。

学生第一次未匹配、尚未补材料时，服务器返回“需要材料”的业务结果，不伪造一个已提交状态。补交本人上传的材料后才生成待审核记录。修改姓名或学号可重新尝试名册自动核验。

## 管理、权限和材料

- 后台统一保留“学生认证”入口 `/user/verification`。同一页面内包含“学生名册”和“认证审核”两个页签，共用学校选择和统计；不再提供单独的“学生名册”菜单。旧 `/user/student-roster` 地址自动跳转到该统一入口并保留查询参数。
- 查看需要 `user:view`，审核、导入、修改规则需要 `user:cert`；学校管理员还受所属区域限制。配置学校管理员时同时分配查看与审核权限。
- 审核必须携带申请 ID 和当前资料版本；并发审核只有一次生效。提交、更正、通过、驳回、撤销和学籍变更留历史记录。
- 账号绑定使用数据库唯一约束及事务保护；并发匹配同一学生不会批准两个账号。
- 新上传学生证转换为去除元数据的 JPEG，存储在私密材料表。本人或有该学校权限的管理员通过鉴权接口读取，不生成公开图片链接。历史材料保持版本关联。
- 常规服务器日志不保存学生认证请求正文或检索参数；详细证据放在学校范围内的处理记录。
- 认证状态以学校启用状态、当前有效学籍和账号绑定判断，按实际服务区域校验。发布、圈子等独立认证开关继续生效。
- 后台审核后强制重新读取结果，学生端立即采用服务器的通过/待审核结果，不固定写成待审核。

既有历史照片的公开对象存储地址未批量迁移或修改 ACL；新上传采用私密材料机制。历史照片治理属于后续上线前应核对的现状，不能把新接口保护误称为旧图片链接已经失效。

## 发布准备

增量 SQL：

- MySQL：`backend/prisma/additive-migrations/mysql/202609170002_student_identity_roster.sql`
- PostgreSQL：`backend/prisma/additive-migrations/postgresql/202609170002_student_identity_roster.sql`

SQL 只包含本次学生认证增量，不包含骑手提现变更，不删除旧表，不导入名册，不切换学校认证方式。默认 `MANUAL`，老记录默认 `LEGACY`。PostgreSQL 增量脚本已经实际执行验证；MySQL 脚本由对应 Prisma schema 生成，但本机没有可用的 MySQL 实例，尚未实际执行。正式服务器使用何种数据库，应以发布前检查为准，不把 PostgreSQL 的通过结果当成 MySQL 验收。

发布步骤：

1. 确认目标数据库版本、线上代码基线和本次发布文件；隔离当前工作区中其他任务的改动，备份数据库与现有应用。
2. 在相同数据库类型的隔离副本验证本次 SQL，确认迁移历史及执行方式；已有库不得用 `db push` 代替正式迁移。
3. 发布配套后端、后台及小程序认证页面。旧小程序仍提交公开照片 URL，不能直接使用新版私密材料接口，需协调小程序版本切换。
4. 在目标学校预览学校提供的 1,000 人名单，核对统计后确认导入。
5. 确认预览统计后提交导入。提交成功会自动把该学校切换为“名册匹配自动通过，未匹配人工审核”；这不自动打开区域所有学生专属服务，服务开关继续分别控制。需要暂停自动匹配时，再在“认证方式”中切回全部人工审核。
6. 用经授权的实际测试账号检查匹配通过、未匹配人工审核、其他学校权限隔离和旧记录保留，再开放使用。

暂停自动审核可把学校方式调回“全部人工审核”，保留新服务及数据。撤销过的认证仍应保持撤销；不能删除新增表、清空历史或直接用旧版本绕过状态检查来回退。
