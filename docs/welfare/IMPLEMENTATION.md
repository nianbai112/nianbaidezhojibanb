# 校园福利抽奖 · 第一版交付说明

完成时间：2026-09-17。本次修改为本地开发与隔离验证，尚未对现有业务数据库执行升级，未部署服务器、未上传小程序。

## 使用入口

- 管理后台：运营与系统 → 福利抽奖（`/marketing/welfare`）。沿用 `activity:view`、`activity:edit` 权限和管理员校区范围。
- 小程序：活动列表顶部「校园小幸运」；也可在后台页面路径目录和个人中心菜单编辑器选择「福利抽奖」「我的抽奖」。
- 首页导航可设置路径 `pagesWelfare/index`，个人中心可设置 `pagesWelfare/mine`。

## 第一版做了什么

1. **即刻抽奖**：刮刮卡或点击揭晓，服务器确定结果。后台设置每人每天、整场次数，活动参与上限，奖品份数和单次概率。按北京时间计算每日次数；耗尽的奖项保留概率区间，该区间计为未中奖。
2. **报名开奖**：每人报名一次，先截止报名，再按设定时间统一开奖。报名成功保存凭证，结果留在「我的参与」，用户关闭小程序也不影响开奖。人数不足按实际候选人数抽取，一人最多一个奖品。
3. **奖品**：实物凭 24 位领取码到指定地点核销；优惠券由任务进程自动入账，失败自动重试。券的普通自领次数限制不限制抽奖奖励。
4. **后台管理**：活动草稿、奖品图片、概率、时间、校区、学生认证/会员条件、发布、暂停/恢复、提前结束即刻活动、截止前取消报名活动、参与和发放记录、开奖统计、操作日志、核销。
5. **指定赠送**：只允许真实 `super_admin` 角色配置；限定时活动发布前设置，最多 50 人。额外预留库存，不占随机奖品份数；赠送用户不参与随机抽取。活动详情与名单明确公示该机制，领取页显示「指定赠送所得」。不是暗中内定随机中奖。
6. **页面设计**：奶油底色、珊瑚红按钮、小兔主题，活动中心、抽奖详情、报名/中奖/未中奖结果、我的参与、中奖公示 5 个页面。真实触摸刮除，支持按钮揭晓。

首版为免费参与；没有接入付费、积分扣减、购买换次数、现金红包、邀请换次数、签到奖励和邮寄地址。这些需要单独确定扣款/退款、机会来源和发放规则，不能只靠增加一个后台开关。

## 活动操作约定

- 保存草稿 → 配置奖品 → 如需赠送，保存名单 → 发布。发布时锁定规则，预留所有奖品券库存。
- 已配置赠送名单时，要改草稿奖品，先清空并保存名单，再改奖品和重新选择赠送对象。
- 暂停参与不推迟已承诺的开奖时间；暂停中的定时活动仍会开奖。
- 定时活动只能在报名截止前取消。即刻活动提前结束，不影响此前已获奖用户领取。
- 实物需运营自行备货；核销前核对用户领取码，核销后不得重复交付。
- 指定赠送对象无需重复报名；失效/封禁/已注销账号开奖时跳过。
- 资格在报名时核实并保留；开奖时再次排除失效账号，不因报名后会员自然到期而取消已获得的随机报名资格。
- 单场限制：最多 10,000 次即时抽奖或 10,000 名报名用户，最多 12 个奖项、1,000 份随机奖品。指定赠送额外最多 50 份。

## 后端与数据

新增独立 `WelfareModule`，通过 `AppModule` 提供 HTTP 接口；通过 `WorkerModule` 注册 `WelfareWorker`，每 10 秒检查到期活动及待发奖品券。实际开奖发生在到期后的任务处理时刻，进程故障恢复后补做。

新增 5 张表：`welfare_campaigns`、`welfare_prizes`、`welfare_entries`、`welfare_gifts`、`welfare_draws`。没有复用已退役的评论抽奖。

所有活动写操作首先锁活动行。参与请求编号唯一、报名记录唯一、单场开奖记录唯一；结果、库存和通知同事务提交。数据库提交后的网络重试返回原结果；手机重新进入可恢复已消耗的最后一次抽奖。随机数使用 Node `crypto.randomInt`，统一开奖无放回抽取。

优惠券在发布时占用 `receivedCount` 预留额度；实际发券不重复扣库存；取消/结束释放未中奖的额度，已中奖待发的额度继续保留。不要删除或停用正在作为奖品的券；异常可在参与记录看到，修复券配置后自动重试。

公开接口只返回脱敏昵称、奖品和结果来源；真实用户 ID、内部赠送原因、请求编号和领奖码不进入公开名单。领取码仅本人查询接口返回，管理员列表不暴露领取码。

## 微信消息

站内结果通知写入既有持久投递队列，独立于微信订阅消息。

新增订阅场景 `welfare_draw`，报名成功页只在已有启用模板时显示订阅按钮，用户主动授权后才能接收微信提醒。后台「微信通知」能看到该场景。**没有编造模板 ID 或模板字段**：上线时需按微信平台实际可用模板配置 `WechatTemplate` 的模板 ID、字段映射及启用状态。可映射数据包括 `activityName`、`prizeName`、`result`、`drawTime`、`title`、`content`；类型及长度需匹配选定模板。结果页跳转由通知本身携带。

## 升级方式与建议

**A（推荐）：** 先在测试环境导入本次增量 SQL，启动 API 与 Worker，再在开发版小程序验收，最后按原有发布流程上线。可以逐项核对实际奖品券、权限、微信模板。

**B（不推荐）：** 直接覆盖线上文件、让 ORM 自动重建全部表。现有工程已有其他改动和历史迁移，整库重建会扩大变更范围，并影响历史数据。

本次增量 SQL：

- PostgreSQL：`backend/prisma/additive-migrations/postgresql/202609160001_welfare_draws.sql`
- MySQL：`backend/prisma/additive-migrations/mysql/202609160001_welfare_draws.sql`
- 标准 PostgreSQL migration 同步保存到 `backend/prisma/migrations/202609160001_welfare_draws/migration.sql`。

部署时只选择对应数据库的一种升级路径执行一次；不要同时执行增量 SQL 与同名标准 migration。按已有工程迁移登记规范处理已执行记录。执行前备份数据库并核对 5 张新表尚不存在。脚本仅创建本功能的表、索引和关系，不包含删除旧表/旧字段。

升级后运行项目既有 `db:generate`、后端构建、后台构建，重启 API 和 Worker。只启动 API 不会触发自动开奖与券发放。小程序新增原生 Page 位于 `pagesWelfare`；当前前端是编译产物工程，今后如果从另一份 uni-app 源码重新编译覆盖，必须同步保留/迁移本模块和入口改动。
